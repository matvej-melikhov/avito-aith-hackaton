# Avito AI Reviewer — описание проекта (промежуточная версия)

Чекпоинт 4 сентября 2026. Самостоятельный документ — состояние проекта на эту дату зафиксировано здесь, без ссылок на рабочие материалы, которые продолжают меняться.

## Аннотация

Движок проверки домашних работ по требованиям с человеком в контуре решения. Координатор описывает задание и критерии, система готовит по каждой работе черновик проверки с цитатами из текста, ревьюер подтверждает или правит. Первый профиль — проверка домашних заданий Авито Образования, ядро спроектировано так, чтобы переносилось на другие сценарии проверки без переделки.

## Проблематика

У процесса проверки нет единого состояния: работа лежит в GitHub или Stepik, критерии — в условии, статус — в Google Sheets, переписка — в мессенджере. Заказчик сам это формулирует: «данные приходится сверять между несколькими системами, а при ручном переносе могут возникать ошибки или задержки». Три пласта нагрузки: координация методиста (до 10 ч/нед), само ревью (5–10 ч/нед на эксперта), ввод в строй ревьюеров (доступы, калибровка, вычитка новичков) каждый поток заново.

## Постановка задачи

Кейс требует прототип с тремя обязательными функциями (распределение работ, предварительное ревью по критериям, сигнал об использовании ИИ), минимум тремя дополнительными, сквозное демо и тестирование пре-ревью на трёх и более вариантах решения одного задания. Жёсткое ограничение: решение по студенту принимает человек, ИИ не ставит оценку и не применяет санкции.

## Техническое решение

Ядро одинаково для любого сценария: взять артефакт, взять свод требований, разложить требования на три класса и проверить каждое подходящим способом, выдать вердикт с цитатой, отдать человеку, записать в журнал. Три класса требований:

| Класс | Пример | Кто проверяет |
|---|---|---|
| Формальные | «построена диаграмма C4» | код, без модели |
| Содержательные | «есть декомпозиция по двум признакам» | модель находит и цитирует, код проверяет цитату |
| Оценочные | «обосновано ли соблюдение SRP» | только человек |

На реальной рубрике системного дизайна формальные и содержательные требования уже дают 4.5 из 6 баллов надёжно. Адаптеры (источник артефакта, приёмник результата) и координация (распределение, сроки) вынесены за пределы ядра и подключаются профилем.

Отдельное решение недели: координатор описывает задание один раз, без автоизвлечения критериев из готового условия — риск, что структурированные критерии можно скормить модели целиком, подтверждён реальным случаем (см. ниже). Ревьюер сам тянет работы из общего пула под заявленную ёмкость, а не получает их от координатора.

## Реализованные компоненты

На эту неделю сделано: продуктовая постановка и метрики, разбор текущего процесса, архитектура ядра с адаптерами, модель данных из 16 сущностей с ER-диаграммой, полный реестр из 23 экранов по трём ролям в виде кликабельного макета, контракты (что нельзя нарушать), 10 гипотез с порогами провала, интервью с реальным ревьюером курса Tech QA. Рабочего кода пока нет — это следующий шаг.

## Предварительные результаты

Интервью с реальным ревьюером дало факты вместо допущений: ручная проверка занимала около часа на работу, с их собственным навыком для модели — 10–15 минут, реальное ускорение в 4–6 раз. Масштаб потока — около 100 студентов, минимум 5–6 ревьюеров на тип задания. Три класса требований и принцип «сигнал об ИИ — не запрет, а решение человека» уже так работают у Авито, не только в нашем дизайне.

## Ограничения

Итоговую оценку и спорные случаи решает человек — не автоматизируем принципиально. Сигнал об использовании ИИ не влияет на балл автоматически. Персональные данные студентов не покидают контур: работаем с ID, не с ФИО. Оценочные критерии остаются за человеком на обозримое время — это не наше решение, а то, как уже работает Авито по факту интервью.

## Открытые вопросы

Не закрыты вопросом к кейсодателю: какой контур допустим для моделей, приемлема ли стоимость проверки, можно ли получить реальные баллы по критериям для калибровки, как решить риск «слишком точные критерии — уязвимость» для идеи саморевью.

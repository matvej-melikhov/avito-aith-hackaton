# 05. Что делаем на этой неделе и что оставляем на потом

> **Статус:** ранний срез MVP. Текущие границы продукта зафиксированы в `docs/platforms/review-platform.md` и `specs/001-backend-core/spec.md`; при расхождении приоритет имеют они. Перед реализацией нужен единый program-scope с очередностью backend, AI-компонента и трёх интеграций.

## Что делаем

**Сервис забирает сданные работы, распределяет их по ревьюерам с учётом загрузки, готовит по каждой работе черновик проверки по требованиям задания с цитатами и сигналом об использовании ИИ, а после подтверждения ревьюером фиксирует результат и уведомляет студента.**

Ревьюер вместо «прочитай двадцать килобайт и придумай оценку» получает «проверь девять готовых вердиктов и подтверди».

## Рамки пилота

Одно задание, один канал сдачи, две роли.

- **Задание:** системный дизайн, лабораторная 1. Лабораторная 2 как проверка переносимости.
- **Канал:** GitHub. Остальные каналы объявлены адаптерами, но не реализованы.
- **Роли:** ревьюер и координатор. Студент получает обратную связь и, если успеем, саморевью.
- **Второй профиль:** задание по Tech QA, другой формат файлов и другой канал. Доказывает, что смена сценария это настройка.

**Почему такой выбор.** У системного дизайна требования уже лежат таблицей с баллами, решения в Markdown, есть семь работ с известными уровнями для замера качества, а механика GitHub видна прямо в материалах кейса. Альтернатива, Tech QA плюс Google Sheets, сильнее по проверкам кодом, но слабее смотрится в демо, поэтому идёт вторым профилем.

## Полный список возможностей и приоритеты

Одна таблица вместо двух. Приоритет означает следующее:

- **Ядро** — без этого нет сквозного сценария, режется только вместе с проектом.
- **Обязательно** — прямо требуется условиями кейса.
- **Желательно** — заметно добавляет ценности, отсутствие переживём.
- **Развитие** — показываем на слайде, в код на этой неделе не идёт.

| Возможность | Приоритет | Комментарий |
|---|---|---|
| Требования задания как файл настроек | **Ядро** | без этого не работает ничего остальное |
| Проверки кодом по формальным требованиям | **Ядро** | самая надёжная часть, стоит дёшево |
| Проверка по каждому требованию моделью с цитатой | **Ядро** | главная ставка проекта |
| Проверка цитат кодом | **Ядро** | без неё ревьюер не доверяет и перепроверяет всё сам |
| Карточка ревьюера: вердикты, цитаты, подтверждение | **Ядро** | то, что показываем на демо |
| Журнал: предложение системы, правка человека, финал | **Ядро** | доказательство участия человека |
| Распределение работ с учётом загрузки | **Обязательно** | требование кейса, детали в [09](09-assignment.md) |
| Сигнал об использовании ИИ с основаниями и уверенностью | **Обязательно** | требование кейса, детали в [08](08-review-core.md) |
| Черновик обратной связи студенту | **Обязательно** | часть требования про рекомендации ревьюеру |
| Сроки, напоминания, расчёт штрафа | **Обязательно** | дополнительная функция, правило штрафа есть в самом задании |
| Выгрузка результата в Google Sheets | **Обязательно** | дополнительная функция, названа в кейсе. Один адаптер, полдня |
| Дашборд координатора: статусы, просрочки, нагрузка | **Обязательно** | дополнительная функция, снимает основную ручную работу |
| Ревью доработок: что из замечаний закрыто | Желательно | штатный шаг процесса, на рынке почти нет |
| Типичные ошибки потока для методиста | Желательно | закрывает пункт про улучшение учебных материалов |
| Второй профиль задания | Желательно | лучший аргумент про масштабирование |
| Саморевью для студента | Желательно | меняет экономику процесса, детали в [03](03-platform.md) |
| Проверка качества обратной связи новичков | Желательно | снимает с методиста работу второго ревьюера |
| Поиск дублей между работами потока | Развитие | дёшево, но не критично |
| Согласованность ревьюеров между собой | Развитие | нужен объём данных, которого у нас нет |
| Публичный API и вебхуки | Развитие | описываем контракты, не реализуем |
| Ревью кода в CI, проверка документации на стандарты | Развитие | показываем таблицей профилей |
| Кабинет студента как полноценный интерфейс | Развитие | не в этой неделе |
| Своя платформа курсов | Не делаем никогда | это ловушка «мы придумали стартап» |

Дополнительных функций по кейсу нужно минимум три. В строках «обязательно» и «желательно» их семь, то есть запас есть даже после сокращений.

## Порядок отказа, если не успеваем

Режем строго в этом порядке, сверху вниз:

1. проверка качества обратной связи новичков,
2. саморевью для студента,
3. второй профиль задания,
4. типичные ошибки потока,
5. ревью доработок,
6. красивый интерфейс, вместо него простой список и комментарий в пул-реквесте.

**Никогда не режем:** ядро целиком, распределение, сигнал об ИИ, выгрузку результата, замер качества на семи работах, замер времени ревьюера.

## Объём пилота

- **Работы:** семь реальных плюс пятнадцать-двадцать пять сгенерированных нами вариаций с заданными дефектами. Как их делаем и зачем — в [10](10-benchmark.md).
- **Ревьюеры:** четыре-пять выдуманных профилей с разной ёмкостью и темами. Реальных данных о ревьюерах у нас нет, на демо это говорится прямо.
- **Замер эффекта:** шесть работ, три проверяем как сейчас, три с готовым черновиком. Протокол в [10](10-benchmark.md).

## Сценарий демо, четыре-пять минут

1. Координатор описывает задание в форме вручную: текст для студента и девять требований с типами проверки. «Настройка нового задания заняла две минуты». Автоизвлечение из условия это идея на будущее, сейчас только ручной ввод.
2. В пул падают двадцать пять работ, часть после дедлайна. Система раскладывает их на четырёх ревьюеров, показывает загрузку до и после, помечает опоздавших штрафом.
3. Карточка работы: проверки кодом, девять требований с вердиктами и цитатами, предварительная сумма 4.5 из 6, это граница зачёта, поэтому работа уходит на эскалацию. Блок сигнала об ИИ с тремя основаниями. Черновик обратной связи.
4. Ревьюер меняет один вердикт, отклоняет сигнал, правит строку обратной связи, подтверждает.
5. Результат уходит в выгрузку, студент получает уведомление, статус меняется на «проверено».
6. Студент прислал доработку, система показывает, какие замечания закрыты, а какое нет.
7. Дашборд координатора: статусы, просрочки, нагрузка, типичные ошибки потока.
8. Переключаем профиль на Tech QA. «Другой курс, другой формат, другой канал, тот же движок».

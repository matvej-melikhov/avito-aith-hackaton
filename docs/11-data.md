# 11. Данные: что есть, чего нет, что берём

*Термины — в [глоссарии](glossary.md).*

## Что лежит в репозитории материалов

| Папка | Условие | Решения | Сколько | Годится для MVP |
|---|---|---|---|---|
| **`system_design`** | .md, **критерии таблицей с баллами** | .md с диаграммами | 7 работ | лучший вариант |
| **`tech_QA`** | .pdf, критерии на 20 баллов | .xlsx (шаблон Google Таблицы) | 3 | хороший второй |
| `GO` | 3 файла .md | исходники Go (без истории коммитов, без тестов) | 3 | дорого по времени |
| `product_fraud`, `product_business_models` | .pdf с критериями и правилом штрафа | .docx / .xlsx | по 3 | средне |
| `product`, `data_analysis` | .docx | .docx / .pdf / .xlsx | 5 заданий × 3 | средне |
| `data_science` | .docx | .ipynb / .html / исходники | 4 задания | разнобой форматов, дорого |

**Почему системный дизайн — лучший выбор:**
- критерии уже в виде таблицы с баллами (лаба 1 — 9 критериев, 6 баллов, зачёт 4, лаба 2 — 5 критериев, 10 баллов, зачёт 6),
- в условии есть готовый чек-лист «проверочные пункты для преподавателя» — фактически инструкция для нашего агента, написанная методистом,
- решения — обычный Markdown с диаграммами, парсится тривиально,
- **7 работ с известными уровнями** при требуемых трёх,
- канал прописан в условии: «отправлены в Git-репозиторий».

**Почему QA — хороший второй:** ровно 21 тест-кейс, «не более 3 проверок на функционал», обязательные столбцы, есть эталонное решение. Примерно 11 баллов из 20 проверяются кодом. В слабом решении десятки ячеек с текстом `TODO` — такую работу можно отсеять до ревью, без ИИ.

## Чего нет

| Чего нет | Чем это мешает | Что делаем |
|---|---|---|
| реальных ревью и баллов по критериям | нет «правильного ответа» для сравнения | размечаем сами, просим у кейсодателя |
| объяснения, почему работа слабая | самая длинная и полная работа помечена как слабая — непонятно, за что | вопрос №1 кейсодателю |
| пометок «сгенерировано ИИ» | нечем измерить качество сигнала | делаем контрольный набор сами |
| истории коммитов у Go-решений | нельзя анализировать характер работы студента | воссоздаём PR у себя |
| выгрузки Google Sheets | структуру знаем только по скриншоту | просим шаблон |
| данных о ревьюерах и объёмах потока | не на чем показать распределение и посчитать эффект | синтетические профили с явной пометкой |

## Находки, влияющие на функциональность

1. **Правило штрафа есть в самих заданиях:** «досдать в течение 1 дня со штрафом −1 балл, позже — 0 баллов», проверка не более 7 дней. Значит функцию «расчёт штрафа» можно сделать буквально по тексту условия.
2. **Условия требуют самодекларации использования ИИ:** «если вы использовали ИИ — укажите это и опишите, как именно». Это превращает наш сигнал из обвинения в проверку соблюдения правила курса.
3. **Требования к оформлению — готовый список проверок кодом:** объём ≤3 страниц, Arial 11, интервал 1,15–1,5, доступ на комментирование, количество тест-кейсов. Работа с нарушением объёма «может не проверяться» — то есть отсев экономит время ещё до ревью.
4. **Длина не равна качеству:** самая длинная работа (31 КБ) — слабая, «хорошая» — 17 КБ. Модель, скорее всего, ошибётся именно здесь.
5. **Формат обратной связи ревьюера** — короткий список конкретных действий, а не эссе: «Привет, отличное начало! Рекомендации: исправь проброс контекста между слоями, добавь ретрай при пинге к базе…».
6. **Псевдонимизация уже есть** — в таблице студенты под числовыми ID, ФИО передавать не нужно.

## Что берём в работу

**Основное:** системный дизайн, лабы 1 и 2, канал GitHub.
- тестовый набор — **7 работ** с известными уровнями (требуется минимум 3),
- ручная разметка: 4 работы × 9 критериев + 3 × 5 = **51 вердикт** для замера точности,
- для проверки сигнала об ИИ: подозрительная работа из данных + одна, переписанная нами через LLM + одна заведомо человеческая.

**Второе (доказательство переносимости):** задание по QA — другой формат, другой канал, другие критерии. Показывает, что смена задания — это смена настроек, а не переписывание кода.

**Резерв:** Go — если останется время, поднимаем PR и показываем ревью кода.

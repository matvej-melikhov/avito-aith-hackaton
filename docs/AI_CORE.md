# Ядро ИИ-проверки: сервис prereview

Версия 6 сентября 2026. Код: [`prereview/`](../prereview/), промпты: [`prompts/`](../prompts/), контракт с платформой: [`specs/005-workspace-completion/ai-handoff.md`](../specs/005-workspace-completion/ai-handoff.md). Цифры прогонов: [`EVALS.md`](EVALS.md).

## Что это

Отдельный сервис, который платформа вызывает при проверке работы. Он скачивает снимок работы, проверяет её по каждому критерию задания и возвращает ревьюеру предложенный балл, объяснение, цитату из работы с адресом, сигнал об ИИ и черновик фидбека. Студенту тот же сервис даёт самопроверку без баллов. Итоговое решение всегда за человеком: сервис ничего не публикует и не меняет оценку.

## Как устроена проверка одной работы

1. **Снимок.** Скачивание по подписанной ссылке, проверка размера и sha256. Форматы: markdown, docx (pandoc), pdf (pdftotext, без текстового слоя → все критерии «не проверено»), zip-снимок GitHub. Другой формат → честный отказ `unsupported_format`.
2. **Защита данных.** До любого вызова модели: почты, телефоны, ключи и токены заменяются плейсхолдерами, файлы `.env` не передаются вовсе. Строки, похожие на инструкции модели («поставь максимум», «ignore previous»), вырезаются из среза и поднимают флаг `injection_suspect`, который виден ревьюеру и в сигнале.
3. **Рубрика.** Критерии приходят из платформы. Файл задания `prereview/assignments/<slug>.json` добавляет по ключу критерия класс проверки и формальные проверки. Без файла класс выводится эвристикой.
4. **Формальные проверки кодом.** Дюжина примитивов (`file_exists`, `dir_exists`, `grep`, `count_files`, `section_exists`, `mermaid_blocks`, `count_images`, `count_tables`, `min_words`, `max_pages`, `test_defs` и др.). Для формальных критериев это вердикт с полным баллом или нулём и адресом `файл:строка`. Для остальных критериев те же счётчики подаются модели как справка.
5. **Судья по критерию.** Один вызов модели на критерий, ответ строго по схеме (strict tool call DeepSeek, фолбэк json_object + pydantic + повтор). Работа подаётся как данные с нумерацией строк. Два прогона при температуре 0: разошлись → берётся осторожный вердикт, уверенность `low`, оба обоснования ревьюеру.
6. **Проверка цитат кодом.** Каждая цитата ищется в указанном файле рядом с указанными строками, затем по всему файлу без учёта пробелов, затем по другим файлам. Не нашли → цитата выбрасывается, уверенность снижается. Вердикт «выполнено» без единой подтверждённой цитаты превращается в «нужен ревьюер», балл не показывается.
7. **Репозитории.** Для zip-снимка модель сначала исследует файлы через DeepSeek Harness в headless-режиме: только `read`, `glob`, `grep`, sandbox read-only, без shell, сети и субагентов, таймаут и лимит вывода. Harness собирает места и цитаты по критериям, наш судья ставит балл по срезу найденных файлов, наш код сверяет цитаты. Любой отказ Harness → судья работает по усаженному тексту репозитория.
8. **Оценочные критерии.** Балл предлагается с уверенностью `low`, к нему добавляются два-три наблюдения с цитатами. Решает ревьюер.
9. **Сигнал об ИИ.** Отдельный модуль из независимых функций-сигналов с общим контрактом: однородность абзацев, длинные тире, шаблонные связки, остатки диалога, markdown внутри docx, заглушки и «остальной код», комментарий над каждой функцией. У каждого основания есть ограничение «почему это может быть невиновно». Уровень считается правилом, не суммой. Декларация об ИИ в работе сверяется с сигналом. Выход: уровень, основания с адресами, что недоступно (история git, стилометрия), два-три вопроса для Q&A. В баллы не входит, `probability` в контракте всегда `null`.
10. **Черновик фидбека.** Приветствие и 5–7 коротких императивных пунктов из итогов по критериям. Сводка ревьюеру со стоимостью прогона попадает в `reviewer_note` первого критерия.
11. **Журнал.** Каждый прогон пишется в `prereview/data/runs/<run_id>-<attempt>.json`: версии промптов, модель, токены по вызовам, стоимость в рублях и долларах, результаты по критериям с обоими повторами, сигнал, ошибки.

Правила, которые код не даёт нарушить: балл выше нуля только с подтверждённой цитатой; ошибка модели → «не проверено», а не балл; оценочный критерий только с низкой уверенностью; при усадке работы отсутствие не считается провалом; ответ проверяется правилами бэкенда до отправки (ровно те критерии, балл не выше максимума, `requirement_met` для оценочных).

## Контракт с платформой

`POST /v2/review-assists/{run_id}` и `POST /v2/self-reviews/{run_id}`: сервис сохраняет intent по `(run_id, attempt)` в sqlite, скачивает снимок сразу (ссылка живёт 15 минут), отвечает событием `running` и выполняет работу в фоне. `GET …/{run_id}?attempt=N` отдаёт последнее событие, неизвестный прогон → 404. Повторный POST не создаёт вторую работу, другой `input_fingerprint` для той же пары → 409. Отказ подтверждается событием `failed` с кодом `invalid_artifact`, `unsupported_format`, `unavailable` или `invalid_result`. После рестарта незавершённые прогоны продолжаются из сохранённого снимка. Bearer проверяется, если задан `PREREVIEW_TOKEN`. Чек-лист совместимости из `ai-handoff.md` покрыт тестами `prereview/tests/test_service.py` с заглушкой модели.

Самопроверка студента получает только публичные критерии и текст задания: указания ревьюеру и эталон в неё не попадают, баллов в ответе нет.

## Модель за интерфейсом

`PREREVIEW_LLM_PROVIDER=deepseek|fake`, `PREREVIEW_LLM_MODEL` (по умолчанию `deepseek-v4-flash`), `PREREVIEW_LLM_BASE_URL`. Любой OpenAI-совместимый API, в том числе локальный vLLM или модель Авито, подключается сменой этих переменных. Провайдер для демо: DeepSeek по ключу команды, только публичные примеры работ. Тарифы и курс рубля в [`prereview/pricing.json`](../prereview/pricing.json): курс помечен как допущение.

## Запуск

```bash
uv sync --directory prereview
```

Локальная проверка одной работы (файл или каталог репозитория):

```bash
uv run --directory prereview prereview grade "hw_examples/system_design/лаба 1/хорошее.md" -a system_design_lab1
```

Самопроверка студента: добавить `--purpose self`. Без модели: `--fake`. Без Harness: `--no-harness`.

Сервис в docker-стеке платформы:

```bash
docker compose -p workspace-completion-local -f deploy/compose.yaml -f deploy/compose.workspace.yaml -f deploy/compose.ai.yaml up --build -d --wait mysql redis minio ai api
```

Ключ `DEEPSEEK_API_KEY` берётся из `.env` в корне репозитория. Проверка: `curl http://127.0.0.1:18100/health`.

Evals на публичном корпусе: `uv run --directory prereview prereview evals` (корпус клонируется в `hw_examples/`, отчёт в `docs/EVALS.md`).

Тесты: `uv run --directory prereview pytest`.

## Ограничения, о которых говорим прямо

- Снимок GitHub приходит без истории: признаки процесса (один коммит перед дедлайном, авторство) недоступны, сигнал так и пишет.
- Тесты курса в песочнице не запускаются: строки вида «тест проходит» проверяются по коду с низкой уверенностью, фактический прогон за ревьюером. Стенд `grader/codecheck.py` показывает, как это делать офлайн.
- DeepSeek Harness вышел в developer preview 13 августа 2026 и меняется; поэтому есть автоматический фолбэк без него.
- Порог уровня сигнала не калибровался на реальном потоке, объяснение это говорит.
- PDF без текстового слоя (сканы, экспорт досок) не проверяется, критерии уходят ревьюеру.
- Критерий с максимумом в один шаг балла при частичном выполнении уходит ревьюеру: «половину от 0.5» поставить нельзя.

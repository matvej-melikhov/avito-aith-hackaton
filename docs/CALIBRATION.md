# Калибровка ядра проверки: слабые, средние и сильные работы

Версия 6 сентября 2026. Вопрос: оценивает ли система слабые, средние и сильные работы так же, как настоящий ревьюер с таблицей критериев Авито. Короткий ответ: да, там, где метки корпуса согласуются с рубрикой. Там, где расходятся, система и ручная ревьюерская разметка сходятся между собой, а расходятся с меткой.

Данные: публичный корпус `ai-talent-hub-avito/homework_examples`, коммит 7a72e08. Таблица критериев курса Go: `docs/reference/Критерии — Шаблон оценки для ревьюеров.xlsx` (присланный 6 сентября файл побайтно совпадает с ней). Ручная разметка: `prereview/evals/labels/*.json`, один проход по полному тексту каждой работы с этой таблицей в руках. Это не оценки Авито, а наша ревьюерская интерпретация. Спорные строки перечислены в самих файлах разметки.

## Что из этого следует

1. Система не путает сильное со слабым ни на одном корпусе: во всех парах, где метка совпадает с рубрикой, порядок воспроизведён. Две пары, где порядок «нарушен», это пары с сомнительной меткой, и ручная разметка с системой согласна.
2. Калибровать нужно не модель, а рубрику: все найденные расхождения закрылись подсказками к критериям и формальными масками в файле задания, без правки промптов и кода судьи. Это и есть механизм калибровки на пилоте: ревьюер правит балл, расхождение попадает в подсказку строки.
3. Что осталось на пилот: разметка вторым человеком независимо (сейчас один проход), реальные оценки ревьюеров Авито вместо меток «слабое / среднее / хорошее», прогон тестов курса в песочнице для строк класса A.

## Запуск в песочнице (6 сентября, вечер)

С вечера 6 сентября Go-решения не только читаются, но и запускаются: сервис собирает бинарник из снимка, отдельный контейнер-песочница без ключей и без сети гоняет его по сценариям из файла задания (устройство в `docs/AI_CORE.md`, пункт 8). Строки рубрики о поведении сервиса (16 из 40) теперь решаются фактом запуска, а не чтением кода: «как в ТЗ» даёт полный балл с уверенностью `high`, «НЕ по ТЗ» ноль или долю, «сервис не стартовал» оставляет вердикт модели с пометкой ревьюеру.

Покритериально 112 строк из 120 совпали с ручной разметкой точно. Из 36 строк, решённых запуском, совпали 34, и оба расхождения содержательные:

- «Сообщение при остановке» у слабого: песочница видит сообщение «Shutting down gracefully...», по строке xlsx этого достаточно (1.5), по ТЗ нужен точный текст (0). Строка была в списке `_disputed` и раньше. Точный текст песочница проверяет отдельно и пишет в факты, решает ревьюер.
- «Паника при недоступной базе» у слабого: по коду разметка дала 0.5 (есть `log.Fatalf`), запуск показал, что без базы сервис стартует и продолжает слушать порт, потому что пул создаётся лениво и `Ping` при старте не вызывается. Запуск здесь точнее чтения, метка исправлению подлежит.

Остальные шесть расхождений это оценочные строки («качество кода», «тонкие модели», «нет логики в handlers», «пакеты по сущностям»), где модель и раньше колебалась, а решает ревьюер.

Что песочница поймала такого, чего по коду не видно:

- у среднего сервис стартует на захардкоженном 8080 и игнорирует `PORT` из `.env` и флаг `--port`: строки «порт из Env» и «флаг важнее env» получили 0, а «сервер запускается» и «/ping» подтвердились;
- у среднего процесс убит сигналом без обработки (код −15): «остановка по сигналу» 0, как в разметке;
- у сильного лог старта уходит в stderr (пакет `log` по умолчанию), строка «лог в stdout» 0, как в разметке; у слабого свой логгер пишет в stdout, 1;
- у слабого нет миграций: песочница не наказывает CRUD второй раз, пробы к базе не выполняются и строки уходят модели, а строки про миграции получают 0.

Ограничения замера: один аннотатор, три работы, имена переменных окружения студента угадываются по коду и списку общих имён. На публичных репозиториях курса более поздних заданий (воркеры, Kafka) сервис с нашими переменными не стартует, и песочница честно отдаёт «не проверено» с логом, а миграции и паника без базы проверяются всё равно.

## Метрики классификации по строкам рубрики

Считаются скриптом `python prereview/evals/metrics.py --md` по файлам `prereview/evals/labels/` и `prereview/evals/results/` (для Go взяты прогоны с песочницей от 6 сентября, файлы `*__sandbox.json`). Один пример это строка «работа × критерий». Три взгляда на одну таблицу:

- «выполнено полностью»: положительный класс это полный балл по строке;
- «балл выше нуля»: положительный класс это любой ненулевой балл;
- «требует внимания»: продуктовый взгляд. Положительный класс это строка, где по разметке балл ниже максимума. Система сигналит, если предложила меньше максимума или воздержалась. Recall здесь это доля проблемных строк, которые система не пропустила, precision это доля сигналов по делу. Для ревьюера важнее recall: пропущенная проблема уходит студенту без разбора, лишний сигнал он снимает за секунды.

Строки, где система воздержалась («нужен человек»), в мягком варианте исключены, в строгом считаются сигналом. Оценочные строки («качество кода», «тонкие модели», «документация») считаются отдельно, потому что по ним решает ревьюер, а балл модели только рекомендация.

| Корпус | Строк | Взгляд | accuracy | precision | recall | F1 |
|---|---|---|---|---|---|---|
| Лаба 1 (4 работы, 9 критериев) | 36, 1 воздержание | выполнено полностью | 100 % | 100 % | 100 % | 100 % |
| | | требует внимания | 100 % | 100 % | 100 % | 100 % |
| Go 1–3 (3 работы, 40 критериев) | 120, без воздержаний | выполнено полностью | 94 % | 98 % | 92 % | 95 % |
| | | балл выше нуля | 97 % | 99 % | 96 % | 97 % |
| | | требует внимания | 94 % | 89 % | 98 % | 93 % |
| Go 1–3 без оценочных строк | 114 | выполнено полностью | 96 % | 98 % | 95 % | 97 % |
| | | требует внимания | 96 % | 94 % | 98 % | 96 % |

Что стоит за ошибками в Go. Единственный ложный «выполнено» это «сообщение при остановке» у слабого решения, спорная строка из `_disputed`. Единственная пропущенная проблема это та же строка с другой стороны. Остальные расхождения это строки, где система строже разметки: оценочные («качество кода», «тонкие модели»), «нет логики в handlers», «пакеты по сущностям» и «паника без базы», где запуск показал, что паники нет.

Ограничения замера те же, что у всей калибровки: один аннотатор, семь работ, две рубрики. Ста процентов на лабе 1 не стоит читать как «система идеальна»: это 36 строк, размеченных тем же человеком, который правил подсказки к критериям. Честная цифра для слайда это Go: около 95 % по строкам при recall проблем 98 %.

# Почему агент не отличил сильную домашку от слабой

Разбор эксперимента коллеги (Codex, 3 сентября) и попытка построить агента,
который ранжирует работы по силе.

Данные: `ai-talent-hub-avito/homework_examples` — 20 заданий, 58 решений с
метками слабое / среднее / хорошее. Метки взяты как эталон ранжирования.
Код: [`grader/`](../grader/). Модель: `deepseek-chat`, температура 0.

**Главный вывод вперёд.** Ни одна из четырёх конфигураций — включая ту, что
мы строили как «правильную», — не обошла уверенно тривиальную базовую линию
«кто написал больше, тот лучше». Это не значит, что агент невозможен. Это
значит, что **выбранный способ проверки (угадать метку) почти ничего не
проверяет**, и что метрику успеха для системы надо ставить другую.

---

## 1. Что было в эксперименте коллеги

Из расшифровки чата:

- Взяты **2 задания и 8 работ**, обе задачи из трека `system_design`.
- Агент разложил условия на критерии, проставил покритериальные баллы, сложил.
- task1: `слабое_1` — **5,75 / 6**, `хорошее` — **5,5 / 6**, `среднее` — 4,75,
  `слабое_2` — 2,75.
- task2: `хорошее` — 9,5 / 10, `среднее` — 7, `слабое` — **тоже 7**.
- Слепой повтор воспроизвёл результат: 50 из 60 покритериальных оценок совпали,
  по спорной паре — все 18 из 18.
- Агент сам нашёл дефект корпуса: `слабое.md` в task1 — файл из task2.

Формулировка «агент не смог определить, какая домашка сильная» неточна.
Агент **определил и обосновал**; разошлись его вывод и метка, а разрешающей
способности не хватило, чтобы этот спор закрыть.

---

## 2. Диагноз

### 2.1 Провал разрешающей способности, а не ранжирования

Баллы легли в 79–96 % шкалы, порядок решала разница **0,25 балла — 4 % шкалы**.
Агент честно пометил это как «спорную интерпретацию, а не следствие рубрики».

Причина структурная: рубрика почти вся состоит из проверок «есть / нет».
Любая небезнадёжная работа закрывает почти все, суммы упираются в потолок.

Мы воспроизвели эффект на полном корпусе. Наивный протокол (оценить работу
отдельно, балл 0–100) даёт:

- **ничьи в 12 заданиях из 20**, медианный разброс 23 балла из 100;
- **на 25 % пар работ протокол не высказывается вообще** — ставит равные баллы.

Ровно то же `7 = 7`, что у коллеги.

Разложение наивного протокола по типу пары:

| | пар | точность |
|---|---|---|
| модель поставила **разные** баллы | 42 | **78,6 %** |
| модель поставила **равные** баллы (решил алфавит) | 14 | 57,1 % |

Когда модель высказывается — она неплоха. Проблема не в качестве суждения,
а в том, что она **воздерживается на четверти пар**.

### 2.2 Выборка, на которой нельзя делать выводы

2 задания из 20, 8 работ из 58, один трек — причём тот, где метки наименее
надёжны, и с дублем файла между заданиями. Это не диагностика системы, это
один спорный кейс.

### 2.3 Часть требований не проверяется чтением

В ДЗ по backend-разработке критерии «локальный запуск без ошибок» и «все тесты
проходят» — **2 балла из 10**, и текстовая модель их не проверяет, а угадывает.

Мы прогнали все три решения в песочнице: стартуют все три, тесты проходят
12 / 7 / 21. Сгенерированный из условия conformance-тест дал то, чего чтение
не даёт:

| | путь эндпоинта | формат ответа | логика | валидация |
|---|---|---|---|---|
| A | `/predict` ✔ по ТЗ | голый `bool` ✔ | верна | 422 |
| B | `/predict` ✔ | обёртка `{is_valid}` ✘ | верна | 422 |
| C | `/advertisement/predict` ✘ | обёртка `{resp}` ✘ | верна | 422 |

ТЗ требует вернуть «лишь одно булево значение». Две работы из трёх нарушают
контракт ответа, одна — ещё и путь. По критерию «обработчик не соответствует
заданному API — 0 баллов» это решающее различие, и надёжно увидеть его можно
только запуском.

### 2.4 Извлечение текста уничтожает то, что требует рубрика

- `data_analysis / ДЗ 2`: рубрика прямо требует скриншоты («2 балла — верный
  аргументированный ответ, **прикреплённые скриншоты**»). Скриншоты есть только
  у хорошей работы — 3 вложенных изображения. `pandoc` отдаёт их как
  `![](media/image3.png)`; пайплайн, чистящий разметку, теряет решающий критерий.
- `data_analysis / ДЗ 3`, среднее решение — **PDF без текстового слоя**: экспорт
  доски Miro (колонки «Цель и задачи → Валидация проблемы → Генерация гипотез
  → …»). `pdftotext` возвращает 0 символов. Текстовый агент оценивает работу как
  пустую и отправляет в конец рейтинга независимо от содержания.

### 2.5 Обрезка по длине — систематическая ошибка, а не шум

Самый дорогой дефект, и мы сами в него вляпались.

Исходные файлы `data_science / Пример домашки 1` — 561 КБ, 575 КБ, 408 КБ.
После потолка извлечения (60 КБ) и лимита промпта (45 КБ) модель видела
**8–11 % каждой работы**, причём начало HTML-экспорта — это импорты и
boilerplate, а не анализ.

По корпусу: **обрезаны 14 работ из 58 (24 %), в 9 заданиях из 20**, у восьми
потеряно больше 30 % текста.

Обрезка «первые N символов» бьёт **именно по длинным работам** и выкидывает
разделы, по которым различается уровень: выводы, анализ рисков, контр-метрики.
Результат: на этом задании обе LLM-конфигурации дали **0 из 3** пар — полную
инверсию, — тогда как тупая базовая линия по длине дала 3 из 3.

### 2.6 Метки в `system_design` действительно сомнительны

Мы разобрали `слабое_1.md` независимо, не зная выводов коллеги, и сошлись:
работа содержит корректную семантику C4 (Component описывает внутренности
одного контейнера), паттерн outbox, таблицу связности по парам компонентов с
рисками, обоснования границ системы и trade-offs. Она **длиннее** хорошей
(31 КБ против 17 КБ) и содержит больше диаграмм.

Два независимых агента сошлись на том, что метка не соответствует содержанию.
Проверять систему оценивания на самом спорном срезе корпуса — плохая идея.

## 3. Что показывает полный корпус

### 3.1 Базовая линия: «кто длиннее, тот лучше»

Без всякой модели, по одному размеру файла:

```
pairwise accuracy : 71,4 %  (40/56)     [случайно = 50 %]
exact ranking     : 45,0 %  (9/20)      [случайно = 17 %]
находит лучшую    : 65,0 %              [случайно = 33 %]
находит худшую    : 55,0 %              [случайно = 33 %]
```

Монотонность «слабое < среднее < хорошее» по объёму держится в **7 заданиях из
19**. В шести слабая работа — самая длинная (`product` ДЗ 2, ДЗ 4, ДЗ 5,
`product_fraud`, `system_design` лаба 1 и 2). Обе лабы, на которых ставился
эксперимент коллеги, попадают в число худших для этой эвристики: выборка была
не просто маленькой, а самой неудачной из возможных.

### 3.2 Измеренные результаты

| метод | pairwise | exact | лучшая | худшая | совпадение с длиной |
|---|---|---|---|---|---|
| «длиннее = лучше» | 71,4 % | 45 % | 65 % | 55 % | 100 % |
| наивный: балл 0–100 по одной работе | 73,2 % | 45 % | 65 % | 65 % | 69,6 % |
| структурный: доказательства → сравнение | 66,1 % | 35 % | 60 % | 50 % | 73,2 % |
| сравнение по полным текстам | 69,6 % | 45 % | 60 % | 65 % | 66,1 % |
| **сравнение + структурная усадка** | **76,8 %** | 45 % | **70 %** | 65 % | 80,4 % |

Что из этого следует честно читать:

- **Наш «правильный» структурный протокол оказался хуже наивного** (66,1 %
  против 73,2 %). Причина найдена и измерена: стадия сравнения судила по
  сжатым доказательствам — **14 % исходного объёма текста**, — а 82 % находок
  имели статус «present», то есть таблица доказательств почти не различала
  работы. Мы своими руками сузили канал перед финальным суждением.
- Снятие этого бутылочного горлышка дало 69,6 %, замена обрезки на структурную
  усадку — 76,8 %.
- **Но 76,8 % против 73,2 % — это не победа.** McNemar на общих парах:
  7 выигрышей против 5 проигрышей из 56. Разница в пределах шума.
- И лучшая конфигурация **сильнее всех прочих совпадает с базовой линией по
  длине (80,4 %)**. Прямой запрет в промпте «не повышать балл за объём» не
  сработал: у структурного протокола совпадение с длиной даже выросло (73,2 %).

**Вывод: ни одна конфигурация не обошла уверенно тривиальную базовую линию.**

## 4. Что с этим делать

### 4.1 Сменить метрику успеха

Совпадение с трёхуровневой меткой — плохая цель. Метка это мнение одного
ревьюера по всей работе целиком; она шумная (`system_design`), а большая часть
восстановимого из неё сигнала объясняется объёмом. Система, обученная на эту
метрику, будет оптимизировать многословие.

Что мерить вместо:

- **покритериальное согласие с ревьюером** — по строкам рубрики, а не по
  итоговому ярлыку (в шаблоне Авито это уже единица учёта);
- **долю баллов с подтверждающей цитатой** — сколько решений система умеет
  обосновать адресом в работе;
- **долю пар, которые система честно отправляет человеку** вместо угадывания;
- для кодовых треков — **согласие с прогоном** (тесты, conformance), где есть
  объективная истина.

### 4.2 Починить инженерию, которая молча теряет сигнал

Это дало больший прирост, чем любая правка промпта:

| дефект | доля корпуса | что делает |
|---|---|---|
| обрезка «первые N символов» | 24 % работ, 9 заданий из 20 | инвертирует ранжирование на длинных работах |
| потеря вложенных изображений | скриншоты требует рубрика минимум в 2 заданиях | теряет решающий критерий |
| PDF без текстового слоя | 1 работа | работа получает 0 за то, что её не прочитали |
| критерии, требующие запуска | 2 балла из 10 в backend-ДЗ | балл угадывается |

Реализовано в [`grader/`](../grader/): `condense.py` (усадка с сохранением
структуры и явными пометками пропусков), `inventory.py` (программный подсчёт
скриншотов, диаграмм, таблиц, тестов), `extract.py` (детект PDF без текста и
эскалация на vision), `codecheck.py` + `conformance_backend_hw1.py` (прогон
тестов и проверка соответствия ТЗ).

### 4.3 Заставить систему высказываться — или честно молчать

Наивный протокол воздерживается на 25 % пар, и эти пары разрешаются случайно.
Сравнительная рамка убирает воздержания, но там, где работы действительно
близки, правильный ответ — **не угадывать, а поднимать человеку**. У нас для
этого два сигнала, оба уже считаются:

- расхождение вердикта между прямым и обратным порядком подачи работ;
- совпадение итогового порядка с порядком по объёму.

### 4.4 Чего мы НЕ показали

- Что LLM-оценщик лучше подсчёта символов. На этом корпусе — не показали.
- Что покритериальная схема точнее холистической. Не показали.
- Что запрет на «оценку за объём» в промпте работает. Показали обратное.

## 5. Границы

- 20 заданий, 56 информативных пар. Различия в 3–7 п.п. статистически незначимы;
  любые сравнения методов выше — ориентир, а не доказательство.
- Метки — мнение одного ревьюера, а не истина; для `system_design` они
  расходятся и с нашим разбором, и с разбором коллеги.
- Один прогон на одной модели (`deepseek-chat`, t=0). Устойчивость между
  моделями не измерялась.
- Прогон кода реализован для Python/FastAPI и сборки Go; conformance-тест
  написан под одно задание и не обобщён.
- Vision-проход **обнаруживает** работы без текстового слоя, но разбор картинки
  моделью не подключён — сейчас это эскалация человеку.
- Граница «слабое / среднее» размыта сильнее, чем «среднее / хорошее»: находить
  лучшую работу удаётся заметно надёжнее, чем разделять две нижние.

## 1. Что берём из шаблона и что достраиваем

Строка шаблона это уже единица проверки: группа, макс балл группы, текст проверки, «как проверяем», критичность. Достраиваем четыре вещи.

**Вес строки.** В ранних заданиях балл задан только на группу (например, «Грейсфул шатдаун» 5 баллов на 3 строки), в поздних на каждую строку. Правило импорта: если балл строки задан, берём его; если нет, делим балл группы поровну, критичным строкам даём в полтора раза больше и округляем до 0.5; ментор видит предложенные веса и правит. Сумма весов строк равна баллу группы, это проверяет автопроверка.

**Класс проверки.** Кто и как заполняет строку. Четыре класса, раздел 2.

**Семантика «критикал».** Кейсодатель не ответил. Наше решение: критичная строка, провалившаяся в авто-проверке, не режет балл сама, а ставит на группу флаг «критичное не выполнено» и поднимает работу в очереди ревьюера. Правило хранится в рубрике как параметр (`critical_policy: flag | cap_group | zero_group`), по умолчанию `flag`. Если Авито скажет иначе, меняется параметр, не код.

**Итерации.** Колонки «Ревью 1», «Ревью 2», «после Q&A» и формула «сумма максимумов по строкам» переносятся как есть. Вторая итерация запускает пайплайн повторно только по строкам, которые не были на максимуме, и показывает дифф кода между итерациями.

## 2. Отбор критериев: четыре класса и как строка попадает в класс

| Класс | Кто заполняет | Признак строки | Примеры из шаблона | Уверенность |
|---|---|---|---|---|
| **A. Тест** | песочница, тесты курса | в «как проверяем» назван тестовый файл | `hw1/ping_test.go`, `hw1/port_env_test.go TestRunServerWithFlagPort`, `hw2/courier_crud_test.go`, `hw5/unassign_curier_after_deadline_test` | факт |
| **B. Статика** | программа, библиотека примитивов | «вручную», но проверяется по файлам, AST или grep без понимания смысла | «Есть файл go.mod»; «Есть cmd/, internal/, pkg/»; «Точка входа в cmd/<service>/main.go»; «Есть закрытие соединения в defer Close()»; «Используется пакет pgx»; «Везде используется логгер, вызовов fmt.Print нет»; «Нет nolint»; «Добавлен конфиг для линтера»; «Есть defer ticker.Stop()»; «Интерфейсы приватные»; «Нет json/db тегов в моделях бд»; «Миграция не накатывается прямо в main.go»; «Добавлены новые миграции (2 штуки)» | факт, с оговоркой «эвристика» |
| **C. Модель с цитатой** | LLM по релевантным файлам, программа проверяет цитаты | нужно понять код, но ответ подтверждается конкретным местом | «Нет логики в handlers»; «Интерфейсы расположены в месте использования, а не реализации»; «Конструкторы ждут интерфейсы, возвращают структуры»; «Нет ошибок sql в usecase/service»; «Используется паттерн фабрика для расчёта дедлайна»; «Логика назначения соответствует слоистой архитектуре»; «Все зависимости внедряются через конструкторы»; «Есть ретрай при запросе ping» | средняя, повышается при найденной цитате |
| **D. Человек** | ревьюер, модель даёт только наблюдения | оценочное суждение | «Хорошее качество кода (понятные названия, нет циклических зависимостей)»; «Тесты читаемы»; «осознанная альтернатива» структуре; «Тонкие модели и handlers» | низкая, балл не предлагается |

**Как строка попадает в класс.** При импорте рубрики модель предлагает класс и, для B, примитив с параметрами; для C, куда смотреть (пакеты, паттерны файлов); для D, что именно наблюдать. Ментор подтверждает в редакторе, это часть шага «сохранить задание». Решающее дерево:

1. В «как проверяем» есть имя теста → A.
2. Формулировка про наличие файла, папки, пакета, вызова, тега, паттерна в тексте → B, подобрать примитив.
3. Формулировка про то, где что расположено, кто кого вызывает, соблюдается ли слой → C.
4. Формулировка со словами «хорошее», «читаемо», «понятно», «осознанно», «тонкие» → D.
5. Не уверены → C с пометкой, ревьюер решит; после первого потока класс уточняется по его решениям.

**Библиотека примитивов для класса B** (то, что пишем один раз, а потом только параметризуем):
- `file_exists(path_glob)`, `dir_exists`, `file_absent`
- `grep(pattern, scope, expect: present|absent, max_count)` — для `fmt.Print`, `nolint`, `defer .*Close()`, `ticker.Stop()`
- `import_present(module)` — pgx, goose, dig, chi
- `ast_query(kind, filter)` — приватные интерфейсы (имя с маленькой буквы), теги структур в пакете `model`, функции в `main.go`, вызовы SQL вне `repository`
- `count(glob)` — число миграций
- `command(cmd, expect_exit, expect_stdout_regex)` — `go build ./...`, `go vet`, `golangci-lint run`, `make migrate`
- `git_meta(...)` — коммиты, даты, авторы (для ИИ-сигнала и штрафа)
- Для не-кода: `docx_pages`, `docx_font`, `xlsx_rows(sheet, filter)`, `xlsx_columns_present`, `section_exists(heading)`, `link_reachable`

Двенадцать примитивов покрывают все строки класса B в шаблоне Go и формальные требования из условий других курсов (21 тест-кейс, 3 страницы, обязательные колонки).

**Сколько чего в шаблоне Go.** Грубая разметка строк: A около 15%, B около 35%, C около 40%, D около 10%. То есть половина таблицы заполняется без модели вообще, ещё 40% модель предлагает с цитатой, и только каждая десятая строка требует чистого суждения. Это цифра для слайда, после точной разметки уточнить.

## 3. Пайплайн проверки одной работы

Вход: ссылка на PR или репозиторий и коммит, рубрика заданной версии, номер итерации. Выход: заполненная таблица критериев с колонками «Авто», «Почему», флаги, блок ИИ-сигнала, черновики комментариев.

```
1. Забор          клон репозитория на коммит; для docx/xlsx скачивание файла
2. Метаданные     git log: коммиты, время, авторы, размеры диффов; для docx история правок
3. Нормализация   дерево файлов; содержимое с нумерацией строк; для Go карта кода через go/parser:
                  пакеты, типы, интерфейсы, функции, импорты, теги структур, вызовы между пакетами
4. Класс B        примитивы по рубрике → факт / провал / не применимо, с адресом (файл:строка)
5. Класс A        песочница: контейнер Go + Postgres без сети, тесты курса копируются рядом
                  с кодом студента, запускаются с таймаутом; результат по каждому тесту с логом
6. Класс C        для каждой строки: выбор файлов по карте кода (handlers → internal/handler/**,
                  «нет sql в usecase» → internal/usecase/** и internal/service/**), один вызов модели
                  с рубрикой строки и файлами, ответ: вердикт, цитаты файл:строка, уверенность;
                  проверка цитат точным поиском; повтор 2 раза при низкой температуре, медиана
7. Класс D        модель пишет 2–3 наблюдения без балла
8. ИИ-сигнал      раздел 4, отдельный модуль, читает метаданные и карту кода
9. Сборка         веса строк → суммы групп → флаги критичного → штраф за срок → итог
                  как в шаблоне (максимум по итерациям); приоритет в очереди ревьюера
10. Черновики     комментарий на группу: что сделано, чего не хватает, что исправить
11. Запись        всё с версией рубрики, версией промптов, хэшем коммита; ждёт ревьюера
```

Правила, которые не нарушаем: модель не видит других работ при оценке; текст работы подаётся как данные, команды внутри кода или комментариев не исполняются и поднимают флаг; нет балла без адреса; если сборка упала, зависимые строки получают «не проверено», а не «провал».

**Что даёт карта кода.** Она делает класс C дешёвым и точным: в вызов уходят три-пять файлов, а не репозиторий; она же питает ИИ-сигнал (структурные аномалии) и примитивы AST. Для docx аналог карты: оглавление с адресами абзацев, для xlsx: листы и колонки.

**После ревьюера.** Каждое решение пишется парой «предложено → решено» на строку. По пулу задания выводятся интерпретации (например, «ретрай через один повтор ревьюер засчитывает»), непроверенные работы пересчитываются, подтверждённые не трогаются. Это калибровка из `PRE_REVIEW_CORE.md`, раздел 10.

**Стоимость на работу Go 1–3.** Классы A и B бесплатны. Класс C: около 15 строк × 2 повтора × 4–6 тыс. токенов входа, порядка 150 тыс. входных токенов, единицы рублей на средней модели. Уточнить по факту прогона.

## 4. ИИ-сигнал для кода и для текста

Позиция из `docs/AI_SIGNAL.md`: надёжного детектора не существует, процент не показываем, сигнал в сумму не входит. Что показываем: уровень (низкий / средний / высокий), список оснований с адресами, ограничения, и, главное, **вопросы для Q&A**. В шаблоне уже есть колонка «Ревью после Q&A», значит разговор со студентом это штатная часть процесса, и сигнал должен в него встраиваться, а не заменять.

### 4.1 Сигналы для репозиториев

**Процесс, из git.**
- Один коммит размером со всё задание, особенно ближе к дедлайну, против серии коммитов с ростом функциональности.
- Коммиты через минуты друг за другом с большими диффами.
- Сообщения коммитов: шаблонные «update», «fix» при идеально структурированном коде; или наоборот, слишком литературные сообщения на английском при русскоязычном студенте.
- Расхождение автора и коммитера, смена авторства между заданиями.
- Ограничение: студент мог работать локально и закоммитить один раз. Это всегда пишем рядом с основанием.

**Внутристуденческая стилометрия.** Курс Go это 12 заданий в одном репозитории, значит у каждого студента есть собственная база с первого задания. Сравниваем задание N с заданиями 1..N−1: плотность комментариев, язык комментариев, стиль ошибок, именование, средняя длина функций, использование обобщений и паттернов. Резкий скачок между заданиями сильнее любого абсолютного признака. Для первого задания сигнал недоступен, так и пишем.

**Артефакты генерации в коде.**
- Комментарии, объясняющие очевидное, над каждой функцией; докстринги везде при отсутствии тестов.
- Остатки диалога: «Here's the implementation», «Вот реализация», `// TODO: implement` без реализации, `// ... rest of the code`.
- Неиспользуемые функции и импорты, «заглушки на будущее», которых не требует ТЗ.
- Переусложнение относительно задания: слои и абстракции, которых ТЗ не просит в этом задании (ЧА в задании 1, когда она требуется в задании 3).
- Единый безликий стиль без следов отладки: нет закомментированного кода, нет `fmt.Println` в истории коммитов вообще.

**Несоответствие ТЗ.** Задание требует конкретики: лог `Shutting down service-courier` дословно, флаг `--port`, `HEAD /healthcheck` с 204, goose для миграций. Сгенерированный по общему промпту код часто аккуратен, но промахивается мимо этих деталей: другой текст лога, другой инструмент миграций, лишние эндпоинты. Полированный код с промахами по конкретике ТЗ это сильный признак, и он же виден в тестах класса A.

**Декларация.** Курсы просят указать, где использовали ИИ. Поле декларации в описании PR. Сигнал сверяется с декларацией: задекларировано → нарушения нет, только совет ревьюеру проверить понимание; не задекларировано и основания есть → вопросы на Q&A.

### 4.2 Сигналы для текстовых работ

Метаданные docx и Google Docs (история правок, время создания и правки, автор); несоответствие конкретике условия (не использованы данные из условия, требования про количество не соблюдены при идеальном стиле); артефакты генерации (остатки диалога, markdown-разметка в docx, типовые связки); нереалистичные числа в расчётах; стилометрия относительно прошлых работ студента. Готовые детекторы текста подключаем как один слабый сигнал с явной пометкой о ложных срабатываниях на русском.

### 4.3 Как считаем уровень

Не сумма баллов, а правило: **высокий**, если есть хотя бы два независимых основания из разных групп (процесс, стиль, несоответствие ТЗ) и нет декларации; **средний**, если одно сильное или два слабых; **низкий** иначе. Порог калибруется на пуле: если высокий у 80% потока, порог сдвигается и об этом пишется методисту. Каждое основание с адресом и с ограничением.

### 4.4 Вопросы для Q&A

Главный выход сигнала. Система генерирует два-три вопроса по найденным местам: «Почему для расчёта дедлайна выбран паттерн фабрика, а не функция?», «Что произойдёт, если Postgres недоступен при старте, покажите в коде». Ответы на Q&A ревьюер фиксирует в колонке «после Q&A». Так сигнал превращается из подозрения в проверку понимания, что и просил кейс: «повод для разговора, а не доказательство».

## 5. Как узнаем, что работает

- **Класс A** проверяется сам: тесты либо проходят, либо нет. Наша задача убедиться, что тесты курса запускаются в песочнице на всех трёх примерах Go 1–3.
- **Класс B** проверяем вручную один раз на трёх работах: каждый примитив либо нашёл то, что есть, либо нет. Ожидаем близко к 100%.
- **Класс C** размечаем сами: двое независимо ставят вердикт по строкам класса C на трёх работах Go и четырёх работах лабы 1; расхождение между нами это базовая линия. Метрики: совпадение вердикта, доля подтверждённых цитат, стабильность между повторами, ложные «не найдено».
- **Класс D** не оцениваем: там нет правильного ответа, смотрим только, что модель не пытается ставить балл.
- **ИИ-сигнал**: на трёх работах Go известны метаданные; сгенерируем одну работу моделью с нуля и одну «полированную» и проверим, что уровень различается и основания осмысленны. Честно пишем: выборка мала, детектор не валидирован.
- **Порядок работ**: суммы должны ставить слабое < среднее < хорошее.

## 6. Что строим первым

1. Импорт xlsx-шаблона в рубрику с автоклассификацией строк и весами. Без этого нет ничего.
2. Нормализация Go-репозитория и карта кода.
3. Примитивы класса B, дюжина штук.
4. Песочница и прогон тестов класса A на трёх примерах. Если тестовых файлов курса у нас нет, пишем свои по ТЗ заданий 1–3, это два часа.
5. Класс C: один промпт, проверка цитат, повторы.
6. Сборка таблицы и итог как в шаблоне.
7. ИИ-сигнал: git-метаданные, несоответствие ТЗ, артефакты, вопросы для Q&A. Стилометрию, если останется время.
8. Второй формат для масштабируемости: лаба 1 системного дизайна в markdown через те же классы B, C, D.

## 7. Решения, принятые без кейсодателя

- «Критикал» = флаг и приоритет в очереди, не автоматический срез балла. Параметр рубрики.
- Веса строк без явного балла делятся поровну с надбавкой критичным.
- Пул с ёмкостью по умолчанию, закрепление студентов как настройка курса, липкость на досдачах.
- Тесты курса, если их нет в доступе, заменяем своими по ТЗ и помечаем как «наши тесты».
- ИИ-сигнал не влияет на балл и превращается в вопросы для Q&A.
- Модель за интерфейсом, демо на API с гарантией необучения и анонимизацией, целевая точка локальная модель.

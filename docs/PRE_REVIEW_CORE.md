# Ядро пре-ревью: рубрика, разделение проверок, формат выхода, итоговая оценка

Зона 2 из `CONTEXT_PACK.md`, раздел 7b. Проектный документ, без кода. Версия: 3 сентября 2026, до встречи с Дашей. Открытые решения собраны в разделе 8.

Что уже зафиксировано на Q&A и на что опираемся:
- Критерии — только те, что в условии. Скрытых нет. Эталонных решений нет, ориентироваться на них не надо.
- Работы проверяются независимо друг от друга, не сравниваются между собой.
- Калибровка ревьюеров один раз перед проверкой, критерии во время курса не меняются.
- Финальное решение по каждому критерию за ревьюером. Сигнал об ИИ не влияет на балл.

Три принципа ядра:
1. **Нет балла без основания.** Каждая предложенная оценка сопровождается цитатой из работы или явным «не найдено, искали там-то».
2. **Детерминированное проверяется кодом, содержательное — моделью, оценочное — человеком.** Модель предлагает, человек решает; чем субъективнее критерий, тем ниже уверенность и тем обязательнее человек.
3. **Рубрика — данные, а не промпт.** Один и тот же движок читает рубрику любого курса; масштабирование на новый курс — это новая рубрика, а не новый код.

## 1. Модель рубрики

### 1.1 Что реально бывает в условиях

Разобрали все восемь направлений из `homework_examples`. Условие — это не только таблица критериев, а пять слоёв, и все они нужны для проверки.

| Слой | Что это | Примеры из реальных условий |
|---|---|---|
| Критерии с баллами | Таблица или список «критерий → макс. балл» | Системный дизайн лаба 1: 9 критериев, макс. 6, зачёт 4. Tech QA: 5 критериев на 20 баллов. Продуктовый фрод: 0–1, 0–4 и т. д. |
| Дескрипторы уровней | Что означает 0, 1, 2, 3 балла по критерию | A/B-тест: «MDE рассчитан корректно, указаны трафик, дисперсия, альфа, бета, расчёт приложен — 3 балла». Data Analysis: «2 балла — верный аргументированный ответ со скриншотами, 1 — верный, но не аргументирован, 0 — неверен» |
| Требования и DoD | Списки «что должно быть», без баллов | Лаба 1: функциональные и нефункциональные требования, Definition of Done. Лаба 2: «тест-кейсы (проверочные пункты для преподавателя)» — готовый чек-лист |
| Формальные ограничения и гейты | Формат, объём, канал, что делает работу непринятой | Фрод: «не более 3 страниц, иначе может не проверяться», «должна быть видна история изменений, иначе работа не принята». Tech QA: ровно 21 тест-кейс, не более 3 на функционал, «отклонение от формата не принимается» |
| Правила процесса | Дедлайн, штрафы, политика по ИИ | Фрод: досдача 1 день со штрафом −1, позже — 0; «необоснованное использование ИИ — снижение баллов; если использовали — укажите как» |

Отдельный случай — курс Go: баллов в условии нет вообще, но требования проверяемы машиной: `GET /ping` → 200 и `{"message":"pong"}`, `HEAD /healthcheck` → 204, порт из `.env` и флаг `--port`, лог `Shutting down service-courier` на SIGTERM, миграции через goose.

Вывод: рубрика в системе должна уметь представить все пять слоёв, иначе половина условий не ляжет.

### 1.2 Сущности рубрики

Описание сущностей словами; формат хранения — JSON, одна рубрика на задание на поток, версионируется.

**Задание (Task).** Курс, направление, название, канал сдачи (GitHub / Stepik / Docs / файл), ожидаемые артефакты (один md, репозиторий, docx, xlsx), дедлайн, ссылка на исходное условие.

**Рубрика (Rubric).** Версия, статус (черновик / подтверждена / заморожена), кто подтвердил, когда. Содержит:
- **Критерии (Criterion)** — единица оценивания. Поля: id, название, макс. балл, тип (см. 1.3), кто оценивает, дескрипторы уровней (если есть), список проверочных пунктов, «обязателен для зачёта» (колонка «Мин. балл» в лабах), источник — дословная цитата из условия, откуда критерий взят.
- **Проверочные пункты (CheckItem)** — атомарные «есть / нет / частично» под критерием. Пример под критерием «Указаны типы взаимодействий и контракты»: «для каждого интерфейса указан формат», «описаны входы», «описаны выходы», «описаны ошибки». Пункты либо взяты из условия дословно, либо выведены из требований и помечены как «выведено» — такие обязательно подтверждает человек.
- **Гейты (Gate)** — условия приёма работы: формат, объём, канал, история правок, число тест-кейсов. Результат гейта — «принята / не принята / принята с пометкой». Провал гейта не ставит 0 автоматически, а поднимает работу ревьюеру с флагом, потому что в условиях написано «может не проверяться», а не «не проверяется».
- **Правила штрафов (Penalty)** — правило расчёта по дате сдачи. Применяется после суммы баллов, отдельной строкой, чтобы ревьюер видел «7 баллов, −1 за просрочку, итог 6».
- **Политика по ИИ (Policy)** — что курс разрешает, требуется ли декларация. Влияет только на текст рекомендации ревьюеру, не на балл.
- **Калибровочные заметки (Calibration notes)** — то, что методист или эксперт добавил после встречи ревьюеров: «под “обоснованием SRP” считаем достаточным один абзац на компонент». Хранятся отдельно, помечены как «не из условия», видны ревьюеру. Это единственный источник критериев помимо условия, и он явный.

### 1.3 Типы критериев и кто их оценивает

| Тип | Признак | Кто оценивает | Уверенность по умолчанию | Примеры |
|---|---|---|---|---|
| Формальный | Проверяется по структуре, счётчику или метаданным без понимания смысла | Код (детерминированно) | Высокая, факт | Объём ≤ 3 страниц, ровно 21 тест-кейс, есть колонка «Ожидаемый результат», есть диаграмма C4, репозиторий собирается, `/ping` отвечает |
| Содержательный | Нужно понять текст и сверить с требованием, ответ проверяем цитатой | LLM-судья, ревьюер подтверждает | Средняя или высокая, если есть дескрипторы и найдена цитата | «Для каждого риска указан тип», «контракты описывают ошибки», «H₀ и H₁ сформулированы измеримо», «в тест-кейсе конкретные значения, а не “от 1 до 5”» |
| Оценочный | Требует экспертного суждения о качестве, обоснованности, читаемости | Ревьюер; LLM даёт черновик с низкой уверенностью | Низкая всегда | «Обоснование архитектурных решений», «читаемость схем», «глубина анализа рисков», «качество описания проверок (7 баллов)» |

Правило: у критерия с дескрипторами уровней модель может предлагать балл по уровню. У критерия без дескрипторов (только «макс. 7 баллов») модель предлагает не балл, а список найденного и ненайденного по проверочным пунктам плюс диапазон; балл ставит человек. Это защищает от псевдоточности.

### 1.4 Как рубрика извлекается из условия

Пайплайн один раз на задание:

1. **Нормализация условия.** Markdown, docx, PDF со Stepik → единый текст с сохранением таблиц. Ссылки на внешние документы (требования в Google Docs, макеты в Figma, шаблон таблицы) фиксируются как «внешние вводные», которые надо приложить руками.
2. **Извлечение моделью** в структуру из 1.2. Модель обязана для каждого критерия и гейта указать дословную цитату из условия. Всё, что выведено из требований, а не написано как критерий, помечается «выведено».
3. **Линтер рубрики** — детерминированные проверки, которые ловят ошибки самих условий. На реальных данных нашлось: в Data Analysis ДЗ 3 написано «6 критериев», а ниже «5 критериев»; в ДЗ 4 сумма баллов 10, но рядом «каждый этап 0–2»; в A/B-тесте «максимум 1 балла» и уровень «0 баллов» склеен с двумя описаниями. Линтер проверяет: сумма максимумов равна заявленному максимуму; у каждого уровня есть балл; нет критериев без источника; гейты не противоречат критериям; порог зачёта достижим. Это готовый доп «предлагать улучшения учебных материалов» из списка кейса, и он получается бесплатно.
4. **Подтверждение человеком** в редакторе рубрики: методист или эксперт, который писал задание, видит критерии рядом с цитатами, правит формулировки, снимает или подтверждает «выведенные» пункты, добавляет калибровочные заметки, замораживает версию. Оценка времени — 10–20 минут на задание, один раз на поток. Это единственный ручной шаг настройки, и он же ответ на вопрос «кто подтверждает».
5. **Заморозка версии.** Работы проверяются по той версии, которая была заморожена на момент дедлайна. Правки идут в следующую версию, что совпадает с практикой Авито «замечания в бэклог следующего запуска».

Что берём в критерии — только условие плюс явные калибровочные заметки. Не берём: эталонные решения (их нет), другие работы студентов (сравнение запрещено), общие представления модели о «хорошей работе». Последнее важно проговорить в промпте: судить только по рубрике, не по вкусу.

Для демо на хакатоне подтверждаем рубрики сами и показываем редактор с линтером как часть сценария координатора.

### 2.2 Детерминированные проверки

Список того, что закрывается без модели и поэтому бесплатно и надёжно:
- Метаданные документов: число страниц, шрифт и размер, дата создания и правки, автор, наличие истории версий (для Google Docs через API ревизий, для docx — по полям и, при наличии, по трекингу изменений).
- Структура: обязательные разделы по заголовкам, обязательные колонки в таблицах, обязательные файлы в репозитории (`cmd/`, `internal/`, `.env.example`, миграции).
- Счётчики: число строк в таблице тест-кейсов, число на функционал, число рисков на этап, число гипотез.
- Наличие артефактов: блоки диаграмм, таблицы, ссылки на расчёт, приложенные скриншоты.
- Дата и штраф.
- Для кода — раздел 2.3.

### 2.3 Автопрогон кода

Для технических курсов у каждого задания есть **спецификация прогона**: список команд и ожиданий, который эксперт пишет один раз вместе с условием, а система выполняет в изолированной песочнице (контейнер без сети, лимит времени и памяти, чистая база в том же контейнере).

Пример для Go, задания 1–3:
- `go build ./...` и `go vet ./...` — собирается, нет предупреждений.
- Запуск с `--port 3000`, затем `GET /ping` → 200 и тело `{"message":"pong"}`; `HEAD /healthcheck` → 204 без тела.
- SIGTERM → процесс завершился, в stdout есть `Shutting down service-courier`.
- Наличие goose-миграции и создания таблицы `couriers` с обязательными полями.
- CRUD: `POST /courier` → 201, повтор с тем же телефоном → 409, `GET /courier/abc` → 400, `GET /courier/999` → 404.
- Структура: слои `handler`, `usecase`, `repository`, интерфейсы на стыках — это уже модель, по коду, с цитатами файлов.

Результат прогона — таблица «ожидание → факт → лог», привязанная к проверочным пунктам рубрики. Если прогон упал на сборке, все зависимые пункты получают «не проверено, сборка не прошла», а не «провалено».

Что не делаем на хакатоне: запуск ноутбуков Data Science с обучением на GPU. Для них ограничиваемся статическим чтением ноутбука и проверкой наличия графиков, метрик и выводов.

### 2.4 LLM-судья: как устроена содержательная проверка

Пайплайн на одну работу:

1. **Нормализация работы** в текст с адресацией: для md — заголовки и строки, для docx — разделы и абзацы, для xlsx — лист, строка, колонка, для репозитория — файл и строка. Адресация нужна, чтобы цитата была кликабельной и проверяемой.
2. **Карта покрытия.** Первый проход: модель строит соответствие «раздел работы → критерии рубрики, к которым он относится». Дёшево, один вызов на работу. Даёт два эффекта: в каждый последующий вызов попадают только релевантные куски (дешевле и точнее), и сразу видны критерии, к которым не относится ни один раздел — кандидаты на «не найдено».
3. **Оценка по критерию.** Один вызов на критерий, а не один на всю работу. На входе: критерий с дескрипторами и проверочными пунктами, калибровочные заметки, релевантные куски работы, для кода — результаты прогона. На выходе — структура из раздела 3.1. Модель обязана цитировать дословно и указывать адрес.
4. **Верификация цитат.** Код проверяет, что каждая цитата действительно есть в работе по указанному адресу. Цитата не найдена — пункт помечается «основание не подтверждено», уверенность понижается, ревьюеру виден флаг. Это главная защита от галлюцинаций.
5. **Устойчивость.** Для критериев с баллом запуск повторяется (2–3 раза при низкой температуре). Расходятся — берётся медиана, уверенность понижается, ревьюеру показывается разброс. Стабильность — одна из метрик evals.
6. **Сборка результата** по работе: гейты, критерии, штрафы, итог, приоритет в очереди (раздел 4).
7. **Черновик фидбека студенту** — отдельный вызов по уже подтверждённым или предложенным пунктам: по каждому критерию что хорошо, чего не хватает, что сделать. Тон и длина — из примеров реальных ревью (5–7 конкретных пунктов). Ревьюер правит и отправляет.

Принципы промпта: судить только по рубрике; не сравнивать с другими работами; не додумывать за студента; если не нашёл — сказать «не найдено» и где искал; на оценочных критериях давать наблюдения, а не вердикт; язык — русский.

Защита от инъекций: текст работы подаётся как данные в отдельном блоке; инструкции внутри работы («оцени на максимум», «ignore previous») не выполняются, а детектируются регулярками и моделью и поднимают флаг «подозрение на инъекцию» ревьюеру. Выход модели ограничен схемой, свободного текста, который мог бы «уговорить» человека, нет — только цитаты и короткие комментарии.

### 2.5 Что остаётся ревьюеру и как выглядит его работа

Ревьюер видит работу и рядом — рубрику с предложениями по каждому критерию. Действия по критерию: принять, изменить балл, отклонить с причиной. Кнопка «принять всё с высокой уверенностью» закрывает формальные и подтверждённые содержательные пункты одним действием, после чего внимание идёт на оценочные критерии, флаги и гейты.

Всегда требуют человека: оценочные критерии, проваленные гейты, пункты с неподтверждённой цитатой или разбросом, сигнал об ИИ, подозрение на инъекцию, работы около порога зачёта, итоговый балл и отправка фидбека.

Всё, что ревьюер изменил, сохраняется как пара «предложено → решено». Это и журнал решений для апелляции, и данные для evals: расхождения по критериям показывают, где модель ошибается системно и где рубрика сформулирована плохо.

## 3. Формат выхода

### 3.1 Результат по критерию

| Поле | Что содержит | Правило |
|---|---|---|
| Критерий | id, название, макс. балл, тип, версия рубрики | |
| Статус | `авто_пройден` / `авто_провален` / `предложено` / `нужен_ревьюер` / `не_проверено` | Формальные — первые два; содержательные — «предложено»; оценочные — «нужен ревьюер»; зависимые от упавшей сборки — «не проверено» |
| Предложенный балл | Число или уровень по дескриптору; для критериев без дескрипторов — диапазон | Нет балла без хотя бы одного основания |
| Уверенность | высокая / средняя / низкая + одна фраза почему | Понижается при: нет дескрипторов, цитата не подтверждена, разброс между запусками, «выведенный» пункт |
| Основания | Список: цитата, адрес (файл и строка / раздел / лист и ячейка), к какому проверочному пункту относится, что подтверждает | Каждая цитата верифицирована кодом; неподтверждённая помечена |
| Не найдено | Список проверочных пунктов, по которым основания нет, с указанием, где искали | Обязательно, чтобы «нет» было проверяемым |
| Комментарий ревьюеру | 1–2 предложения: суть и на что посмотреть | Не убеждать, а направлять |
| Черновик фидбека студенту | Что сделано хорошо, чего не хватает, что исправить | Конструктивно, конкретно, со ссылкой на требование |
| Флаги | `гейт`, `цитата_не_подтверждена`, `разброс`, `инъекция`, `внешняя_вводная_не_приложена` | |

### 3.2 Результат по работе

Заголовок: студент (ID), задание, версия рубрики, время сдачи, номер попытки. Блок гейтов: каждый с фактом и решением. Блок критериев: таблица из 3.1. Блок ИИ-сигнала: уровень, основания, ограничения, декларация студента. Блок штрафов. Итог: сумма предложенная, сумма подтверждённая, порог зачёта, статус. Приоритет в очереди ревьюера (4.4). Для повторной попытки — дифф по критериям: что изменилось относительно прошлой версии, какие замечания закрыты.

### 3.3 Пример на лабе 1 по системному дизайну

Критерий «Указаны типы взаимодействий и контракты (формат, входы/выходы/ошибки)», макс. 1, обязателен для зачёта на 0.5.

- Статус: предложено. Балл: 0.5 из 1. Уверенность: средняя — контракты есть, ошибки описаны не для всех интерфейсов.
- Основания: раздел 5.2, «POST /bookings — тело запроса … ответы 201, 400, 409» — подтверждает входы, выходы, ошибки для одного интерфейса; раздел 5.1, таблица типов — подтверждает «указаны типы взаимодействий».
- Не найдено: описание ошибок для события `booking.created` (раздел 5.2, блок Event); искали в разделах 5 и 6.
- Комментарий ревьюеру: три REST-контракта полные, событие без раздела ошибок; решить, тянет ли на 1.
- Фидбек студенту: «Контракты REST описаны полно, включая коды ошибок. Для события booking.created добавьте, что происходит при сбое доставки и повторной обработке — это часть контракта по условию».

Критерий «Обосновано соблюдение SRP при декомпозиции», макс. 0.5, тип оценочный.

- Статус: нужен ревьюер. Балл: диапазон 0–0.5, не предложен. Уверенность: низкая — критерий оценочный.
- Основания: раздел 2.3 «Обоснование соблюдения SRP», 8 абзацев по одному на компонент.
- Наблюдение: обоснование есть для всех компонентов; глубину оценивает ревьюер.

### 3.4 Правила, которые не нарушаем

- Нет балла без основания. Нет «не выполнено» без «где искали».
- Цитаты дословные и проверенные кодом.
- Оценочные критерии не получают точного балла от модели.
- Сигнал об ИИ не входит в сумму и не показывается как процент.
- Один и тот же формат для всех курсов: меняется рубрика, не схема выхода.

## 4. Итоговое оценивание и ранжирование

### 4.1 Порядок расчёта

1. Сумма подтверждённых баллов по критериям. До подтверждения показывается как «предложено», после — «подтверждено», обе цифры видны.
2. Гейты: провал показывается отдельно с рекомендацией по правилу курса («может не проверяться»); решение о нуле — ревьюер или координатор.
3. Штрафы по правилу рубрики отдельной строкой.
4. Порог зачёта и обязательные для зачёта критерии (колонка «Мин. балл» в лабах): зачёт только если сумма ≥ порога и каждый обязательный критерий набрал минимум.
5. Округление по правилу курса, если задано; иначе без округления.
6. Итог утверждает ревьюер; при изменении после утверждения — новая запись в журнале с причиной.

Где курс задаёт веса в процентах, а не баллах, рубрика хранит веса, движок тот же.

### 4.2 Ранжирование — три разных смысла

**Студентов между собой не ранжируем.** Это прямое следствие ответа Марии и методологии: работы оцениваются независимо, по критериям. На защите это надо проговорить как осознанное ограничение.

**Ранжируем очередь ревьюера.** Какие работы открыть первыми, чтобы человек тратил внимание туда, где модель не справится. Приоритет складывается из: провален гейт; сигнал об ИИ средний и выше; есть неподтверждённые цитаты или разброс; сумма около порога зачёта (± один критерий); много оценочных критериев с большим весом; повторная попытка; близость дедлайна проверки. Работы с высокой уверенностью по всем пунктам идут последними и закрываются быстро.

**Ранжируем в evals.** Проверяем, что предложенные суммы упорядочивают известные работы как «слабое < среднее < хорошее». Это тест системы, а не продуктовая функция.

### 4.3 Что показываем координатору

Распределение подтверждённых баллов по критериям на потоке: критерии, где все теряют баллы (сигнал о качестве материала), критерии с наибольшим расхождением «предложено → решено» (сигнал о нечёткой рубрике или о разбросе ревьюеров). Это доп «аналитика качества проверки» из списка кейса, и она следует из формата выхода без отдельной разработки.

## 5. Evals: как поймём, что ядро работает

### 5.1 Что есть

| Направление | Формат | Условие | Решений | Метки |
|---|---|---|---|---|
| Системный дизайн, лаба 1 | md | с таблицей критериев и «Мин. балл» | 4 (2 слабых, среднее, хорошее) | по работе целиком |
| Системный дизайн, лаба 2 | md | критерии + чек-лист преподавателя | 3 | по работе целиком |
| Go, задания 1–3 | репозиторий | без баллов, проверяемые требования | 3 | по работе целиком |
| Tech QA | xlsx | критерии + жёсткие формальные | 3 | по работе целиком |
| Продуктовый фрод | docx | критерии с дескрипторами, гейты, штрафы, политика по ИИ | 3 | по работе целиком |
| Продукт, A/B и ещё 4 ДЗ | docx, xlsx | подробные дескрипторы уровней | по 3 на ДЗ | по работе целиком |
| Data Analysis, 5 ДЗ | docx, pdf | простые 0/1/2 | по 2–3 | по работе целиком |
| Data Science | ipynb, html | описательные критерии | много | по работе целиком |

Баллов по критериям нет ни у одной работы. Это главное ограничение, и его закрываем сами.

### 5.2 Собственная разметка как базовая линия

Двое из команды независимо оценивают по рубрике лабу 1 (4 работы × 9 критериев) и фрод (3 работы). Расхождение между ними — базовая линия субъективности, с которой сравниваем модель. Это честный ответ на вопрос жюри «а насколько точна модель»: «она расходится с экспертом не сильнее, чем два эксперта между собой» либо «сильнее, и вот на каких критериях». Третий человек разбирает расхождения и фиксирует эталонную разметку.

### 5.3 Метрики

- **Порядок**: доля пар работ, где предложенная сумма упорядочивает их так же, как метка.
- **Покритериальное совпадение** с нашей разметкой: точное и в пределах одного уровня; отдельно по типам критериев — ожидаем высокое на формальных, среднее на содержательных, низкое на оценочных, и это нормально.
- **Достоверность оснований**: доля цитат, подтверждённых кодом; доля критериев с хотя бы одним основанием.
- **Стабильность**: расхождение между повторными запусками.
- **Полнота «не найдено»**: доля реально отсутствующих элементов, которые модель назвала отсутствующими, и доля ложных «не найдено».
- **Экономия времени** — не измеряем на хакатоне, а оцениваем: сколько критериев закрывается «принять всё» без правок.

### 5.4 Прогон самой рискованной гипотезы сегодня

Гипотеза: пре-ревью по рубрике на лабе 1 упорядочивает работы правильно и даёт основания, которые ревьюер принимает без правок хотя бы по половине критериев. Порог провала: порядок нарушен или больше половины цитат не подтверждаются. Отдельно смотрим на «слабое_1» — самую длинную работу с меткой «слабое»: если модель ставит её выше «хорошего», это и есть разговор про длину против содержания и про ИИ-признаки.

Затем тот же движок без изменений на фроде (docx) и Tech QA (xlsx) — это демонстрация масштабируемости через рубрику, а не через код.

### 5.5 Что честно скажем, если не сработает

Список критериев, где модель системно ошибается, с примерами; ограничение размера выборки; отсутствие покритериальных меток от Авито. По правилам недели за честный список ограничений дают баллы.

## 6. Стоимость, порядок величины

Работа по лабе 1 — около 30 тысяч символов, это порядка 10–12 тысяч токенов. Карта покрытия — один вызов на всю работу; девять критериев — девять вызовов с релевантными кусками, в среднем 3–4 тысячи токенов входа каждый; повторы для устойчивости удваивают содержательные вызовы; черновик фидбека — один вызов. Итого порядка 60–80 тысяч входных токенов и 10 тысяч выходных на работу. На моделях среднего класса это единицы рублей за работу, на старших — десятки. Поток в 200 работ на одно задание укладывается в тысячи рублей, что несопоставимо с часами эксперта. Точные цифры считаем после выбора модели и показываем как «стоимость одной проверки и одного потока».

## 7. Что покажем на демо из этой зоны

1. Редактор рубрики: условие слева, извлечённая рубрика с цитатами справа, предупреждения линтера, кнопка «подтвердить версию».

4. Отчёт evals: порядок, совпадение с нашей разметкой, достоверность цитат, стабильность — на трёх форматах.

## 9. Как методист добавляет новое задание

Кто: методист регистрирует задание, эксперт-автор задания подтверждает рубрику и, для кода, спецификацию прогона. Когда: при публикации задания, до дедлайна. Это единственный ручной шаг настройки, и он повторяет то, что методист и так делает сейчас: пишет критерии и калибрует ревьюеров.

### 9.1 Мастер добавления, шаг за шагом

1. **Регистрация.** Курс, название, ссылка на условие (GitHub md, страница Stepik, Google Docs, файл), канал сдачи, что сдают (репозиторий, docx, xlsx, ссылка), дедлайн, правило штрафа. Пять полей, пять минут.
2. **Подтягивание условия.** Адаптер забирает условие и приводит к тексту с таблицами. Ссылки на внешние вводные (требования в Docs, макет в Figma, шаблон таблицы) система показывает списком: «приложите, иначе проверка по ним невозможна».
3. **Извлечение рубрики.** Модель достаёт пять слоёв с цитатой на каждый элемент и предлагает тип каждого критерия: формальный, содержательный, оценочный.
4. **Автопроверка.** Сумма баллов, уровни, источники, достижимость порога, противоречия в тексте. Предупреждения видны рядом с рубрикой.
5. **Редактор.** Методист или эксперт правит формулировки, меняет типы, снимает или подтверждает «выведенные» пункты, для формальных критериев подтверждает способ подсчёта («21 тест-кейс» → число строк на листе), добавляет калибровочные заметки.
6. **Спецификация прогона для кода.** Из требований вида «GET /ping → 200» модель генерирует команды и ожидания, эксперт правит и подтверждает. Для нетехнических заданий шаг пропускается.
7. **Сухой прогон без реальных работ.** См. 9.2. Результат: система показывает, что рубрика различает полную, неполную и формально нарушающую работу.
8. **Заморозка версии** и привязка к потоку и дедлайну. С этого момента работы принимаются в пул.

### 9.2 Холодный старт: примеров хороших и слабых работ нет

Четыре способа, от дешёвого к надёжному, применяются вместе.

- **Синтетические работы с известными дефектами.** Модель генерирует три варианта решения по условию: полное; с намеренными пропусками (например, нет ошибок в контрактах, нет диаграммы последовательностей); формально нарушающее (четыре страницы вместо трёх, 18 тест-кейсов вместо 21). Дефекты заданы нами, поэтому ожидаемые результаты известны. Это проверяет, что рубрика и пайплайн работают и что «не найдено» ловится. Это не проверяет качество суждений модели, и так это и надо подавать.
- **Работы прошлого потока.** Задания живут между запусками, меняются только критерии. Если у Авито есть работы и оценки прошлого потока, они становятся калибровкой. Вопрос Даше.
- **Теневой режим на первых работах потока.** Первые 5–10 работ ревьюер проверяет как обычно, система проверяет параллельно и показывает результат после того, как ревьюер поставил свою оценку. Расхождения по критериям попадают методисту: где модель системно расходится с человеком, там либо формулировка критерия нечёткая, либо нужна калибровочная заметка. Методист правит, выходит новая версия рубрики, режим переключается на помощника. Это главный механизм: рубрика учится на решениях самого ревьюера через журнал «предложено → решено».
- **Мини-калибровка экспертом.** Эксперт оценивает одну синтетическую или первую реальную работу прямо в редакторе. Его решения по оценочным критериям сохраняются как заметки: что считать достаточным.

### 9.3 Признаки готовности задания

- У каждого критерия есть тип, балл, источник-цитата.
- Автопроверка без ошибок или ошибки явно приняты методистом.
- Для формальных критериев задан способ подсчёта; для кода спецификация прогона проходит на «полной» синтетике.
- Сухой прогон различает три синтетические работы ожидаемым образом.
- Указано, есть ли внешние вводные и приложены ли они.

### 9.4 Незнакомый формат сдачи

Адаптеры нормализации ограничены: md, docx, xlsx, pdf, репозиторий, ipynb. Если формат не поддержан (Figma, видео, презентация), задание регистрируется в режиме «только процесс»: распределение, очередь, дедлайны, формальные проверки, фиксация результата, без пре-ревью содержания. Продукт остаётся полезным, а новый адаптер добавляется без переделки остального. Это и есть «масштабирование без полной переработки архитектуры» из критериев кейса.

### 9.5 Откуда берутся работы

Регистрация задания задаёт, за чем следить: GitHub — организация, шаблон репозитория, ветка или метка PR; Stepik — список сдач через API или экспорт со ссылками; Docs — форма со ссылкой. По дедлайну система собирает пул, проверяет доступность ссылок и права, дальше идёт распределение.

### 9.6 Что показать на демо

Экран координатора: «Добавить задание» → вставить ссылку на условие → рубрика с предупреждениями автопроверки → подтвердить → система сгенерировала три синтетические работы и показала сухой прогон → «готово к приёму работ». Затем тот же путь для docx-задания, чтобы показать, что новый курс — это новая рубрика, а не новый код.

# System design: платформа проверки домашних работ

Версия 4 сентября 2026, вечер. Сводит три источника: замороженный контракт бэкенда Владимира (`specs/001-backend-core/`, ветка `backend`), продуктовые решения Матвея (`docs/03`, `04`, `08`, `09`, `platform-screens/`, ветка `matvej`) и проект ИИ-проверки stn (`docs/GRADING_SYSTEM.md`, `docs/PIPELINE.md`). Принцип на всю неделю: **сначала база, потом логика по необходимости.** Каждое место, где мы выбрали простое, помечено «база», расширение помечено «потом».

---

## 1. Одной фразой и границы

Три компонента с жёсткими границами: **бэкенд платформы** хранит состояние и правила процесса, **веб-интерфейс** показывает три роли, **сервис ИИ-проверки** по замороженному контракту получает работу и критерии и возвращает предложения по каждому критерию плюс сигнал об ИИ. Бэкенд никогда не знает про модель, сервис проверки никогда не знает про пользователей и статусы. Финальный балл ставит человек через бэкенд.

Что не входит в базу: автораспределение, песочница для запуска кода, калибровка на пуле, импорт рубрик из файлов, Stepik-выгрузка оценок (описана, не реализуется без платного курса), саморевью студента.

## 3. Сквозной поток данных

```
Координатор ──К4/К5──▶ Backend: Homework + HomeworkVersion + CriterionSet (digest)
                                 │ publish → CourseRunHomework, ссылка для Stepik
Студент ──С1──▶ Backend: preflight ссылки → submit_work → SubmissionVersion
                                 │ worker: захват ArtifactVersion в S3 (SHA / hash)
                                 │ open ReviewIteration (queued), работа в общем пуле
                                 │ start_ai_review → AIReviewRun(fingerprint)
                                 ▼
                       Taskiq worker ──HTTP POST request──▶ AI Review Service
                                                              │ скачивает артефакт по artifact_download.url
                                                              │ нормализация → факты → модель по критериям
                                                              │ верификация цитат → сигнал → черновики
                                                              ▼
                       Backend ◀──POST /v1/internal/ai-review/events (partial…succeeded)──┘
                                 │ suggestions сохраняются отдельно от ReviewRevision
Ревьюер ──Р2 «Взять»──▶ Backend: responsibility event, статус in_review
Ревьюер ──Р5──▶ видит критерии аккордеоном: предложенный балл, «почему», цитаты, флаги, сигнал
                 меняет баллы, пишет фидбек → save_review_revision (draft)
                 publish_review → ReviewRevision(published), total_score
                                 │ outbox → доставки: Stepik / GitHub / email
Студент ──С5──▶ видит результат; при доработке новая SubmissionVersion → новая итерация
```

Три инварианта потока: предложения ИИ живут отдельно от человеческих ревизий и никогда их не перезаписывают (FR-057, FR-078); поздний или устаревший результат уходит в историю (FR-058); AI-review не блокирует человека (FR-055).

## 4. Контракт бэкенд ↔ сервис проверки

Источник истины: `specs/001-backend-core/contracts/ai-review.schema.json`, версия 1.0.0, frozen. Транспорт: бэкенд вызывает сервис по HTTP с телом `request`, сервис отвечает `202` и дальше шлёт события на `POST /v1/internal/ai-review/events` с bearer-токеном компонента. Артефакт скачивается по `artifact_download.url` до `expires_at`.

**Запрос** (что получаем): `run_id`, `input_fingerprint` (jcs-sha256-v1 от версий и хешей входа), `organization_id`, `review_iteration_id`, `artifact` (provider github или google_docs, `content_digest`, `object {key, media_type, byte_size}`, `metadata`), `artifact_download`, `homework {version_id, title, student_text, digest}`, `criteria {set_id, digest, items[{id, key, title, description, max_points}]}`.

**Событие** (что отдаём): `attempt_id`, `attempt_number`, `event_id`, `sequence`, тот же `input_fingerprint`, `status ∈ running | partial | succeeded | retryable_failed | action_required`, `is_final`, `suggestions[]`, `ai_signal`, `error`.

**Suggestion на критерий:** `criterion_id`, `status ∈ suggested | needs_human | not_checked`, `proposed_points` (null при not_checked), `reason`, `evidence[{locator, quote, verified}]`, `confidence ∈ low | medium | high`, `reviewer_note`, `student_feedback`, `flags[]`. Финальное событие содержит ровно одно предложение на каждый критерий.

**ai_signal:** `level ∈ none | low | medium | high | insufficient_data`, `evidence[]`, `limitations[]`, `questions[]`.

**Как наши сущности ложатся в контракт** (база, без изменения контракта):

| Наше | В контракте |
|---|---|
| класс проверки критерия (формальный, содержательный, оценочный) | `flags: ["class:formal"]` и т. п., определяется сервисом по тексту критерия |
| «чего нет и где искали» | в `reason` отдельным предложением и `flags: ["not_found"]` |
| результат детерминированного факта | `evidence.locator` вида `check:section_exists(...)`, `quote` = найденный фрагмент, `verified: true` |
| неподтверждённая цитата | `evidence.verified: false` + `flags: ["unverified_evidence"]`, `confidence: low` |
| оценочный критерий | `status: suggested`, `proposed_points` заполнен, `confidence: low`, `flags: ["class:judgment"]` |
| ошибка модели по критерию | `status: not_checked`, `flags: ["model_error"]` |
| подозрение на инъекцию | `flags: ["injection_suspect"]` на всех критериях + `limitations` в сигнале |
| вопросы для Q&A | `ai_signal.questions` |
| стоимость и версии промптов | в `metadata` локального журнала сервиса; в контракт не входят |

**Потом:** контракт 1.1 с полями `homework.reviewer_notes` (рекомендации ревьюерам), `homework.reference_solution` (эталон), `criterion.check_class` и `criterion.check_spec`. До этого сервис живёт без них.

## 5. Сервис ИИ-проверки: устройство базы

```
POST /ai-review/runs  (request по контракту)  → 202
  └─ фоновая задача run(request):
       1. fetch       скачать артефакт, проверить sha256 против content_digest
       2. normalize   md / zip-репозиторий / docx → документ с адресами
                      (md: заголовки и строки; репозиторий: файлы и строки; docx: абзацы)
       3. facts       детерминированные проверки, выведенные из текста критериев:
                      наличие блока (C4Context, sequenceDiagram), наличие раздела, счётчики,
                      объём; результат в виде evidence с locator "check:…"
       4. classify    класс критерия по тексту (кешируется по criteria.digest)
       5. judge       один вызов модели на критерий: критерий + текст задания + факты
                      + релевантные срезы документа (по заголовкам, бюджет ~12k токенов)
                      → JSON по схеме, температура 0, prompt_version в записи
       6. verify      каждая цитата ищется в документе по locator, потом по всему тексту;
                      не найдена → verified:false, confidence↓, флаг
       7. signal      список функций-сигналов: однородность абзацев, тире и типографика,
                      шаблонные связки, остатки диалога, несоответствие вводным задания,
                      git-метаданные если есть; уровень по правилу; вопросы для Q&A
       8. drafts      один вызов: student_feedback на критерий (императив, коротко) и
                      reviewer_note
       9. events      partial после facts (быстро видно формальное), succeeded в конце;
                      retryable_failed при недоступности модели, action_required при
                      недоступном артефакте
      10. record      локальный журнал: request, ответы модели, токены, стоимость,
                      версии промптов, длительности
```

**Что упрощено в базе и почему.**
- Тулы у модели не вызываются: факты считаются до модели и подаются в промпт. Проще, воспроизводимее, дешевле. Потом: те же проверки как инструменты, если понадобится динамический выбор.
- Один вызов на критерий, без повторов. Потом: второй прогон при низкой уверенности.
- Срезы документа выбираются по заголовкам и ключевым словам критерия, без карты кода. Потом: AST для репозиториев.
- Сигнал об ИИ только из текста и метаданных, без стилометрии между заданиями. Потом: сравнение с прошлыми работами студента.
- Один формат артефакта в базе: Markdown-документ из GitHub (лаба 1). Второй: docx (фрод) как проверка переносимости. Потом: zip репозитория Go, xlsx.

**Промпты** лежат в `prompts/` с версией в имени и выводятся на защите. Модель за интерфейсом `LLMClient` с реализацией `deepseek` и заглушкой `fake` для тестов; смена провайдера в конфиге.

**Стоимость** считается на прогон из usage ответа и тарифа провайдера, пишется в журнал и отдаётся в UI через `reviewer_note` первого события (потом: отдельное поле в контракте).

## 6. Данные и хранение

- **Бэкенд:** MySQL для состояния, S3 для снимков артефактов, Redis как брокер, transactional outbox для доставок. Все сущности с `organization_id`, UUIDv7, UTC. Модель данных в `specs/001-backend-core/data-model.md`.
- **Сервис проверки:** без базы пользователей. Локальный журнал прогонов (SQLite в базе, Postgres потом): `runs`, `attempts`, `criterion_results`, `llm_calls`. Кеш ответов модели по ключу `(prompt_version, model, hash(входа))` для повторяемости evals и экономии.
- **Персональные данные:** в запросе от бэкенда нет ФИО, только идентификаторы. Сервис дополнительно маскирует почты, телефоны и ключи в тексте артефакта до вызова модели. Содержимое артефакта не логируется целиком, только адреса цитат.

## 7. Процессные решения, принятые в базе

| Вопрос | База (делаем) | Потом |
|---|---|---|
| Распределение | общий пул, ревьюер жмёт «Взять», может вернуть в пул; зависшие дольше трёх дней подсвечиваются, координатор жмёт «Напомнить». Ничего не назначается автоматически | рекомендация «следующая работа» из бэкенда по дедлайну и продолжению итерации; калибровочная выборка |
| Создание задания | конструктор в платформе: текст для студента, критерии (формулировка, балл, описание «что считается выполненным»), порог зачёта, правило штрафа, рекомендации ревьюерам, эталон | импорт из файлов |
| Класс проверки | не задаётся координатором, сервис выводит сам | поле в конструкторе и в контракте |
| Оценочные критерии | модель ставит балл с `confidence: low`, ревьюер меняет любой балл | режим «только наблюдения» как настройка задания |
| ИИ-сигнал | уровень, основания, ограничения, вопросы; процента нет, как в контракте; в баллы не входит; студенту не показывается | стилометрия, сверка с декларацией как отдельное поле |
| Итерации | каждая новая сдача это новая ReviewIteration и новый AIReviewRun; результат прошлой остаётся в истории | дифф между итерациями в предложениях |
| Стоимость | считается и пишется в журнал сервиса | поле в контракте, витрина у координатора |
| Задание для демо | лаба 1 по системному дизайну, Markdown из GitHub, 9 критериев, 4 работы | Go 1–3 с шаблоном Авито и песочницей; Tech QA xlsx |

## 8. Отказы и гарантии

| Ситуация | Поведение |
|---|---|
| Артефакт недоступен по ссылке или digest не совпал | событие `action_required` с `error.code = artifact_unavailable`; ревьюер проверяет сам |
| Модель недоступна | факты отдаются в `partial`; финал `retryable_failed`, бэкенд может запустить новую попытку с тем же fingerprint |
| Ответ модели не по схеме | один повтор с указанием ошибки; затем `not_checked` по этому критерию, остальные критерии не страдают |
| Цитата не найдена | `verified: false`, уверенность понижена, флаг; вердикт остаётся, но помечен |
| Работа или критерии изменились, пока шёл прогон | бэкенд помечает результат `stale`, он не становится текущим (FR-058) |
| Дубль события или события не по порядку | бэкенд принимает идемпотентно по `event_id` и `sequence` (FR-077) |
| Инструкции модели внутри работы | вырезаются из срезов, флаг `injection_suspect`, упоминание в `limitations` |

Ни одна ошибка не превращается в балл. Провал критерия ставится только по факту.

## 9. Безопасность и контур

- Аутентификация сервиса проверки перед бэкендом: bearer-токен компонента (`componentToken` в OpenAPI). Бэкенд перед сервисом: общий секрет в заголовке запроса (база) или mTLS (потом).
- Ссылка на артефакт короткоживущая и привязана к организации; сервис не хранит байты дольше прогона.
- Провайдер модели внешний в базе (DeepSeek), поэтому в разработке и на демо только публичные примеры работ. Целевая конфигурация для Авито: локальная модель или модель Авито за тем же интерфейсом, что закрывает требование «данные не покидают контур».
- Логи сервиса без содержимого работ и без ФИО.

## 10. Развёртывание

База: `docker compose` из `deploy/compose.yaml` Владимира (mysql, redis, minio, mailpit, api, worker, outbox-relay, email-worker, mcp) плюс сервис `ai-review` на своём порту с переменными `BACKEND_EVENTS_URL`, `COMPONENT_TOKEN`, `LLM_PROVIDER`, `LLM_API_KEY`, `LLM_MODEL`, `PROMPTS_DIR`. Для разработки сервис проверки запускается и без бэкенда: CLI `grade --request request.json --artifact path` пишет события в файл вместо HTTP.

## 11. Evals: формат набора, который наполняет соседний чат

Каталог `evals/<task_slug>/`:
- `homework.json`: `title`, `student_text`, `criteria[]` в формате контракта (id, key, title, description, max_points), `pass_threshold`.
- `works/<work_id>/artifact.md` (или `.docx`, или `repo.zip`) и `works/<work_id>/meta.json`: `label` (weak / medium / good или synthetic), `known_defects[]` (какие критерии намеренно провалены), `expected[]` по критериям, если размечено вручную, `ai_generated: true|false`, `notes`.
- `runner`: одна команда прогоняет все работы через сервис в режиме CLI, кеширует ответы модели и выдаёт `report.md`: точность по критериям против `expected`, ошибка суммы, зачёт/незачёт, порядок weak < medium < good, доля подтверждённых цитат, доля `needs_human`, стоимость и время; отдельно контрольный вариант «один общий промпт на всю работу».

Пороги из `docs/10-benchmark.md` Матвея: точность по критериям от 75%, ошибка суммы не больше одного балла из шести, зачёт 100%, порядок обязателен. Порог провала главной гипотезы: точность ниже 60% или ревьюер принимает меньше 40% пунктов, тогда режим «выжимка без вердиктов».

## 13. Открытые вопросы

К Владимиру: упаковка артефакта GitHub в `artifact.object` (zip на SHA или файл); адрес и секрет для вызова сервиса; нужна ли `partial`-доставка или достаточно одного `succeeded`; будет ли в 1.1 место для рекомендаций и эталона.
К Матвею: формулировка описаний критериев в конструкторе, потому что сервис выводит класс проверки из текста; согласие, что сигнал показывается уровнем без процента, как в контракте.
Внутри моей зоны: DeepSeek `deepseek-chat` для критериев и черновиков; `deepseek-reasoner` только если evals покажут выигрыш на оценочных.

Как поддерживать дизайн без расхождений

  1. Оставить tokens.css и components.css источниками визуальных правил. В этом предложении исходная палитра и шрифты встроены без изменений; дополнительные классы ограничены префиксом proposal-.
  2. Собирать С1–С3 из одной формы сдачи, Р5–Р6–К9 — из одного компонента критерия с режимом чтения. Общие меню тоже собирать из одного списка для каждой роли. Количество inline-style само по себе не доказывает плохую архитектуру; опасны повторяющиеся правила, расходящиеся между экранами.
  3. Связать сумму, штраф, итог и максимум одной моделью данных. Отдельно определить, меняет ли добавленное ревьюером требование максимум 6 баллов. Не задавать значения суммы вручную в каждой карточке.
  4. У длинных названий предусмотреть перенос; у кода — локальную прокрутку; у баллов и дат — общий столбец. Проверять на реальной ширине 1280 px, а не считать уменьшенный макет 1600 px доказательством адаптивности.
  5. Использовать реальные кнопки, связанные подписи полей и клавиатурное раскрытие. Нынешние span.btn нормальны как рисунок, но не подходят как готовая интерактивная спецификация.
  6. Добавить конкретные состояния основных сценариев: отправка / отправлено / ошибка, взятие работы / уже взята другим, сохранение / ошибка, пустой результат поиска. Они перечислены в дизайн-паке; сейчас их нужно показать, не обещать новые механизмы.
  7. Свести противоречащие формулировки дизайн-пака: крестик или минус у .ck--n; обязательная цитата или её отсутствие у выполненного требования; старые цвета и поведение карточки .card--hard. Компонент, описание и пример должны говорить одно.

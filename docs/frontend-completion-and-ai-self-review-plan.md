# План: все экраны платформы и AI-самопроверка с лимитом

Дата: 2026-09-05. Статус: план расширения, реализация не начата в рамках этого документа.

Цель — завершить все 19 экранов и состояний из `docs/platform-screens/screens.html`, согласовать их с актуальными решениями пользователя и подключить к бэкенду. Студент получает AI-самопроверку до сдачи с обязательным серверным лимитом. Сам AI-компонент разрабатывает другой участник; наша ответственность — контракты, оркестрация, доступ, хранение и интерфейс.

План включает недостающие возможности API. Отсутствие endpoint не исключает экран из объёма: сначала интерфейс проходит сценарий с контрактным имитатором, затем тот же сценарий проходит с настоящим локальным бэкендом. Эти два уровня готовности учитываются отдельно.

### Зафиксировано пользователем

| Решение | Следствие для плана |
|---|---|
| «Avito ID» как отдельной интеграции нет | Удалить эту надпись; использовать действующие способы входа. Не придумывать новый identity provider |
| Рекомендации совместимы со свободным выбором работ | Общий список разрешённых работ сохраняется; рекомендация объясняет приоритет, а не выдаёт исключительное право открыть работу |
| Участие ревьюера неэксклюзивное | Показывать статус и участников. Коллеги могут читать и редактировать; конфликт сохранений обрабатывается через ревизии |
| Балл — число от нуля до максимума критерия | Не восстанавливать обязательный выбор из шкалы `0 / 0,5 / 1` |
| AI-самопроверка студенту нужна | Перенести из исторического later scope в обязательный объём расширения |
| Один лимит на студента и задание в потоке | Ключ учёта: организация + стабильная публикация задания в потоке + студент; новые ссылки, версии требований, попытки сдачи и пересдачи лимит не обнуляют |
| Списывать за полученный результат | Технический сбой не расходует попытку; запуск временно резервирует её, сохранённый валидный результат завершает списание |

### Предлагаемые решения для реализации

- Число попыток — настраиваемое конечное целое `N >= 0` в публикации задания в потоке. `0` означает, что самопроверка отключена. При публикации поле обязательно: `null` и отсутствие настройки не означают бесконечный лимит. «3 попытки» в макете — пример, не согласованное глобальное значение.
- Одновременно у студента выполняется не более одной самопроверки данного задания в потоке. Это ограничение защищает понятность результата и резервирование; оно не заменяет общий лимит.
- Студент видит замечания и результат по открытым требованиям, без предложенного итогового балла, AI-сигнала об авторстве, внутренних заметок и эталона. История запусков и снимков доступна уполномоченному ревьюеру; студент видит пояснение об этом до запуска.
- Основной ревьюер студента и участники конкретной проверки — разные связи. Закрепление помогает упорядочить список, но не блокирует коллег и не переносится автоматически при разовом подключении другого ревьюера.
- Координатор открывает К8 в режиме просмотра, но может явно перейти к разрешённому спецификацией редактированию/публикации. Постоянный запрет для роли methodologist в текущем frontend нужно убрать.

Предлагаемые решения нужны для конкретного плана; они не объявляют прежние несогласованные гипотезы, например жёсткую квоту работ ревьюера, принятыми.

### Дополнительные действия из макетов, которые нельзя потерять между строками

- Довести мастер задания до публикации в конкретном потоке и получения рабочей ссылки для Stepik, хотя третий шаг не имеет отдельного кода макета.
- Восстановить поля комментария к сдаче, эталона и рекомендаций ревьюеру с явной областью видимости.
- Файловую сдачу реализовать отдельным расширением артефактного контракта: загрузка, подтверждение объекта, immutable snapshot, тип/размер и ошибки. Для первой реализации предлагается разрешённый список Markdown/PDF/DOCX; архивы кода и другие типы требуют отдельного согласования с потребителем AI, а не универсального «любой файл».
- Список разрешённых типов файлов и предельные размеры должны быть определены перед backend upload task и отображаться в С1/К4/К5. Пока потребитель AI не подтверждён, экран работает с fixture форматов; production upload не объявляется завершённым.
- Классы критериев и дополнительные требования ревьюера нуждаются в контракте. Для дополнительного оцениваемого требования предлагается новая версия rubric конкретной итерации с явным вкладом в максимум; изменение рубрики общего задания запрещено. Нельзя молча прибавить баллы за пределами существующего max_score.
- В макетах есть порог, штраф первой просроченной сдачи, срок/число доработок и «зачтено/не зачтено». Сейчас из одного `published` эти значения не выводятся. Запланировать отдельную versioned outcome policy: сырой балл, корректировка, итог, решение человека, порог и причина. Предлагаемая базовая конфигурация: без автоматического штрафа; включаемые правила и округление фиксируются в задании. Штраф не вводится автоматически из текста старого макета.
- «Напомнить» оформляется пользовательской командой с конкретными получателями и receipt; отправка не происходит от самого просмотра К6.

## 3. AI-самопроверка: ответственность и контекст

### Разделение с разработчиком AI

| Backend/frontend команды | Внешний AI-компонент |
|---|---|
| Подготовка снимка, права, версии требований, конечный лимит | Модель, промпты, исполнение проверок |
| Атомарный запуск, durable outbox, состояние и повтор доставки задания | Анализ артефакта и формирование результата |
| Доступ к разрешённым входам, проверка event schema/provenance | Версионированные события прогресса/результата/ошибки |
| Сохранение результата и бухгалтерии попыток, student/reviewer projections | Качество замечаний и собственные evals |
| Отображение состояния, истории, ошибок и дальнейшей сдачи | Поддержка согласованных форматов артефактов |

Frontend не обращается к AI-провайдеру напрямую. Выбор провайдера/секрета остаётся серверным. Лимит не передаётся модели как просьба «не проверять больше N раз».

### Что переиспользуется и что добавляется

В текущей реализации `AIReviewRun` и request требуют не-null `submission_version_id` и `review_iteration_id`. Нельзя просто открыть существующий reviewer route студенту или создать фальшивую человеческую итерацию для черновика.

Предлагаемая минимальная модель:

| Объект | Назначение |
|---|---|
| `WorkDraft` | Текущая подготовка работы студента по публикации задания: ссылка/загруженный объект, комментарий, revision. Не является событием окончательной сдачи |
| `PreparedArtifact` | Подготовка и зафиксированный `ArtifactVersion` конкретной версии черновика; незавершённый capture остаётся отдельной Operation |
| `SelfReviewPolicy` | Конечный лимит публикации задания, revision и история изменения; может быть полями существующей сущности, отдельная таблица не обязательна |
| `SelfReviewQuota` | Единственная строка учёта на организацию + публикацию задания в потоке + студента; сериализует резервы и списания |
| `SelfReviewRun` | Логический запуск: владелец, scope, immutable artifact/homework/criteria IDs, fingerprint, версия AI-контракта, result state и quota disposition |
| `SelfReviewAttempt` | Техническая попытка выполнения того же run. Retry провайдера не является новой студенческой попыткой |
| `QuotaEvent` | Append-only reserve/consume/release/admin-adjust с run/request/reason; уникальность терминальной операции учёта на run |

Существующие `ArtifactVersion`, Operation, outbox, leases, provider adapter ports, event authentication, audit/redaction используются повторно. Текущие AIReviewRun/Attempt сохраняют свои строгие связи с человеческим ревью; новый self-review aggregate не требует делать все старые FK nullable. Повторно используемый transport/worker получает строго типизированный контекст, а не произвольный dict.

Fingerprint самопроверки включает назначение `student_self_review`, tenant/владельца/scope, immutable artifact digest, homework/criteria versions, версию контракта. Он не совпадает с fingerprint reviewer-assist и не возвращает закрытый reviewer result. Повторная техническая доставка использует тот же run; отдельный пользовательский запуск — отдельная логическая попытка с отдельным учётом.

## 4. Серверный лимит: точная семантика

Зафиксированные пользователем правила: один общий лимит на задание в потоке; списание за полученный результат.

Ключ quota: `(organization_id, course_run_homework_id, student_user_id)`. Использовать стабильный `course_run_homework_id`, а не номер версии требований или отдельную строку истории публикации.

Поля для интерфейса: `limit`, `used`, `reserved`, `remaining`, `policy_revision`, `active_run_id`. Остаток рассчитывает сервер: `max(0, limit - used - reserved)`. UI не присылает доверенные `used`, `remaining` или `student_id`.

### Когда резервировать и списывать

1. Студент сохраняет черновик. Backend проверяет его принадлежность, публикацию задания и актуальную revision.
2. Команда запуска в одной DB-транзакции revalidate-ит actor, резервирует idempotency receipt, блокирует quota, проверяет наличие попытки и активного run, создаёт run/reservation и durable intent подготовки/проверки.
3. Capture/AI выполняются асинхронно после commit. Ошибка доступа или окончательная ошибка подготовки освобождает резерв. Между проверкой лимита и созданием run нет незащищённого окна.
4. Промежуточные события не расходуют несколько попыток. Результат по этой политике становится доступен студенту после валидного финального события; интерфейс до этого показывает прогресс.
5. В одной транзакции backend сохраняет финальный student-safe result и переводит ровно одну reservation в `consumed`. Повтор event/receipt возвращает тот же результат без второго списания.
6. Получение означает «результат сохранён и доступен студенту», а не «браузер подтвердил чтение»: закрытие вкладки после завершения не отменяет расход.

**Операционное определение результата:** финальное событие нужной версии и fingerprint прошло schema/coverage validation и содержит хотя бы один допустимый вывод по требованию. Это проверка протокола, а не оценка качества модели. Ответ только с технической ошибкой, пустое/невалидное тело или все требования `not_checked` без содержательного результата переводятся в типизированный сбой без списания. Точное разделение `checked/needs_human/not_checked` фиксируется с владельцем AI до заморозки нового контракта; обещание семантической правильности не входит в бухгалтерию лимита.

Результат, который был создан по прежнему снимку и теперь показан в истории как устаревший, остаётся полученным результатом и расходует попытку. Замена ссылки не создаёт возврат задним числом.

| Событие | Состояние попытки |
|---|---|
| Отказ в правах, исчерпанный лимит, невалидная команда | Run/расход не создаются |
| Два одинаковых запроса с одним ключом | Один run и один резерв; возвращается тот же receipt |
| Две вкладки с разными ключами при остатке 1 | Только одна reservation; второй ответ содержит исчерпание/активный run, без AI-dispatch |
| Capture/AI запущен | `reserved`; временно уменьшает доступный остаток |
| Автоматический retry AI | Тот же run/reservation, новый technical attempt |
| Валидный финальный результат сохранён | `consumed` ровно один раз |
| Подтверждённая окончательная техническая ошибка без результата | `released` ровно один раз |
| HTTP timeout, неизвестен исход AI-вызова | Резерв сохраняется, проводится проверка результата; timeout не равен разрешению нового запуска |
| Позднее событие старой technical attempt | Проверяется attempt/fence; не меняет новый результат или quota |
| Повторная сдача, новая ссылка, новая версия задания | Тот же общий quota key |
| Увеличение лимита координатором | Новое значение и audit; прошлые `used` не обнуляются |
| Уменьшение ниже `used + reserved` | Остаток 0; история сохраняется, уже принятый run завершается, новые запуски запрещены |

При обычном неизменном лимите инвариант: `used + reserved <= limit`. После явного уменьшения исторический учёт может превышать новый лимит; не исправлять его отрицательным списанием. Учёт `used >= 0`, `reserved >= 0`, единственность reserve/consume/release и отсутствие новых превышающих запусков сохраняются всегда.

После аварии worker backend восстанавливает run по outbox/lease. При неизвестном результате нельзя автоматически освобождать резерв только по таймеру: сначала запрос состояния или fencing/окончательное завершение попытки. Ручное освобождение зависшего запуска требует прав координатора/оператора, причины и audit. После release поздний результат не становится новым бесплатным student-visible результатом: отклоняется по fence или сохраняется для диагностики без повторного перехода quota. Отдельное ограничение частоты повторяющихся технических ошибок защищает провайдера, но не списывает учебную попытку.

Сдача работы остаётся доступной без AI и при исчерпанном AI-лимите, если допускается правилами самого задания. AI-лимит нельзя использовать как блокировку человеческого ревью.

## 5. Предлагаемые API и контракт с AI

Имена ниже — проект интерфейса для следующего согласования, а не существующие endpoint. Все student IDs выводятся из сессии; все пути и связанные IDs проверяются в tenant/course-run scope. Изменения выполняются через принятый operation-specific command/receipt/revision contract.

| Семейство | Предлагаемая поверхность | Назначение |
|---|---|---|
| Контекст сдачи | `GET /v1/course-run-homeworks/{id}/student-context` | Открытые условия, публикация, черновик, текущая сдача, allowed actions и quota |
| Черновик | `PUT /v1/course-run-homeworks/{id}/work-draft` | Сохранить вход и комментарий, получить draft ID/revision |
| Самопроверка | `POST /v1/work-drafts/{id}/self-reviews` | Start command на точную draft revision; ответ 202 с run/operation/quota |
| Самопроверка | `GET /v1/self-reviews/{id}` | Безопасный результат, snapshot metadata, состояние и ошибки |
| История | `GET /v1/course-run-homeworks/{id}/self-reviews` | История текущего студента и quota; reviewer view получает доступ к конкретному студенту через авторизованный review context |
| Политика | Команда обновления policy публикации задания | Координатор задаёт/изменяет лимит с expected revision; история quota не сбрасывается |
| AI integration | Versioned self-review request/event + callback adapter | Передать задание AI и принять результат по аутентифицированному протоколу |

Для UI нужны типизированные ошибки `self_review_limit_exhausted`, `self_review_in_progress`, `draft_revision_conflict`, `artifact_access_required`, `ai_temporarily_unavailable`, `invalid_ai_result`. У исчерпания/активного запуска response содержит актуальный quota/run ID в безопасной структуре, без необходимости угадывать их по строке message.

### Пакет для владельца AI

- Request: версия контракта, `purpose=student_self_review`, run/attempt identity, fingerprint, ограниченный доступ к неизменяемому артефакту, разрешённое условие и критерии. Никакого секретного provider selection из браузера.
- Для reviewer-assist сохраняется прежний отдельный контекст с review iteration. Старый consumer продолжает получать поддерживаемую версию до явного перехода.
- Event: event ID, attempt ID/number, sequence, fingerprint, статус, финальность, покрытие критериев, student-safe findings, типизированная техническая ошибка. Backend проверяет всю цепочку и принадлежность run.
- Findings: criterion key, проверено/требует внимания/не проверено, понятное объяснение и допустимое основание. Не подменять `not_checked` красным «не выполнено».
- Разработчик AI получает JSON schemas и набор fixtures: успех, отрицательный содержательный вывод, частичный прогресс, пустой ответ, all-not-checked, ошибка, повтор события, неверный fingerprint, stale attempt.
- Backend и AI независимо проходят один набор contract tests. Общий OpenAPI/AI version bump согласуется до реализации клиента: нельзя добавить обязательный `purpose` в frozen 1.1.0 и продолжить объявлять схему прежней.

### Разграничение видимости

Самопроверка использует только разрешённый студенту набор материалов. Эталон, внутренние рекомендации и закрытые поля не передаются в её AI-request: это уменьшает вероятность их пересказа в свободном тексте ответа. Reviewer-assist может получать более широкий контекст через отдельный контракт.

Student response строится allowlist-сериализатором. Простого удаления `reviewer_note` из большого общего payload недостаточно: должны быть отдельные schemas/read projections и тесты для вложенных полей, URL, ошибок и event data. Секреты, model credentials, закрытые ссылки и неопубликованные человеческие решения не попадают студенту. UI не получает скрытый payload «на будущее».

Ревьюер видит число запусков, даты, снимки и разрешённые результаты самопроверок. Это наблюдаемые данные процесса; автоматического штрафа за использование AI и автоматической коррекции оценки они не создают.

Настройки «свои студенты сначала» не реализованы в текущем ранжировании. Это новая политика; не выдавать `continuing_reviewer_id` за основного ревьюера студента. Во всех presets пользователь может открыть другую разрешённую работу. Правила организации/доступа к курсу сохраняются.

Аналитика не требует нового AI-пайплайна. Типичные ошибки первого этапа — агрегаты по явным criterion decisions, без генерации скрытых «инсайтов». Для времени проверки определить измеряемые события и назвать метрику соответственно: интервал started→published не равен активному времени работы. Для расхождения с коллегами нужны сравнимые работы/критерии; при их отсутствии показывать недостаточность данных. Кнопка добавления наблюдения в описание курса показывает редактируемый текст и требует явного сохранения.

Экспорт строится сервером по фильтрам и зафиксированному моменту данных. Проверить дедлайн/права/версию публикации, объём, устойчивость повторного запуска и безопасную обработку CSV/XLSX значений. Студенческая копия использует отдельный набор разрешённых колонок, исключает ревьюерские IDs/заметки и ссылки на работы. Сам факт наличия student ID не позволяет обещать анонимность: название и доступность такой копии уточняются по принятой политике видимости, а не маркируются автоматически «без ПДн».

## 8. Приёмочные сценарии и тесты

### Backend и AI contract

- Две вкладки/два процесса запрашивают последнюю попытку: запускается один run, `remaining` не уходит в минус.
- Повтор start после потери HTTP-ответа возвращает тот же run; повтор финального event не создаёт второй расход.
- Провайдер недоступен до dispatch, capture denied, all-not-checked, невалидный результат: студент не теряет попытку, технический расход наблюдаем отдельно.
- Timeout с неизвестным исходом сохраняет reservation до определения результата; crash между outbox reserve/dispatch/consume восстанавливается без превышения лимита.
- Финальный отрицательный, но содержательный вывод — результат и расход одной попытки; «работа не выполнена» не равно технической ошибке AI.
- Смена URL, GitHub commit, версии задания, номера сдачи и пересдача не создают новый quota bucket.
- Увеличение/уменьшение N, включая N=0 и N меньше истории, сохраняет audit/ledger и блокирует только новые недопустимые запуски.
- Частичные/повторные/переставленные события, stale fingerprint/attempt, revoked credentials и чужой student/tenant не принимаются как текущий результат.
- Student projection, signed artifact URLs и ошибки не содержат reference solution, private rubric fields, reviewer notes, AI credentials или чужие данные.
- Любой разрешённый участник может открыть доступную работу вне рекомендации; два ревьюера видят участие друг друга, конфликтующему save возвращается типизированный conflict.
- Последняя неопубликованная correction не заменяет последнюю опубликованную оценку в кабинете, реестре, статистике и экспорте.

### Frontend и UX

- Для каждого UI-С1…UI-К9 из матрицы: основной сценарий, навигация назад, refresh/deep link, empty/error/forbidden, доступность с клавиатуры и responsive layout.
- С1/С2: загрузка, резервирование, прогресс, результат, исчерпанный лимит, техническая ошибка/возврат, история и несовпадение снимка. Остаток берётся из response, не из localStorage.
- Mock fixtures включают минимум двух студентов, двух ревьюеров, два потока, чужую работу, повторную сдачу, опубликованную и неподтверждённую оценки, quota 0/1/N, зависший запуск и восстановление. Один happy-path fixture недостаточен.
- Р2/К6: рекомендация и общий список показываются вместе; выбор другой работы и подключение коллеги не требуют обхода UI.
- Р5: feedback/баллы не исчезают при 409 и обновлении AI; уход с несохранёнными правками обрабатывается; публикация подтверждает сохранённую версию и не происходит при закрытии модального окна.
- К4/К5: сохраняются поля между шагами, приватность проверяется ответом API, готовая публикация возвращает действующую ссылку.
- К9: CSV и XLSX реально открываются; количество строк, русский текст, дробные баллы, отсутствие закрытых колонок и корректная обработка значений проверены.
- Browser QA: визуально сравнить 19 состояний с макетами с учётом согласованных изменений, проверить минимум desktop и узкий viewport, ошибки консоли и незавершённые действия. Сборка и jsdom-тесты этого не заменяют.

### Два уровня готовности плюс внешняя совместимость

1. **UI готов:** все 19 экранов и действия покрыты сценариями на контрактных fixtures; скрытая заглушка не считается завершённой функцией.
2. **Локальная интеграция готова:** те же сценарии проходят через настоящее приложение backend/DB/worker и mock внешних AI/Stepik/GitHub/Google adapters, с реальной сессией, restart/recovery и разграничением доступа.
3. **Внешняя интеграция подтверждена:** компонент коллеги и конкретные live providers прошли отдельно согласованные gates. Этот уровень не нужен для окончания UI, но обязателен для заявления о готовности соответствующей live-функции.

## 9. Решения, которые нужно конкретизировать до соответствующего пакета

Это не повод откладывать общий план или исключать экраны. Независимые пакеты продолжаются на fixtures; зависимый contract не замораживается с неопределёнными правилами.

| Вопрос | Рабочее предложение | До какого шага |
|---|---|---|
| Значение N | Конечное число задаёт координатор для каждого задания/потока; глобальное значение не выбрано | К4 publication policy / P03 |
| Содержательный результат и частичная проверка | Финальная валидная projection с хотя бы одним содержательным выводом; all-not-checked не расходует попытку | AI handoff / P03 |

| Дополнительное оцениваемое требование | Отдельная rubric version итерации с явным изменением общего максимума; не незаметный бонус поверх старого max_score | P02/P15 |

## 10. Что считается завершением этого плана

Все 19 строк матрицы закрыты evidence по UI и локальному backend; необходимое расширение API реализовано и совместимо по версиям; студент не может обойти лимит, не теряет попытку на подтверждённый технический сбой и может сдать работу без самопроверки; коллеги совместно работают над ревью; закрытые материалы остаются закрытыми. На текущем шаге результатом является только этот проверяемый план. Существующие 17 frontend-тестов и прежние backend checkpoints служат baseline, а не доказательством выполнения расширения.

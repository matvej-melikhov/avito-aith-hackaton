# before-r1 — независимый usability-прогон

Outcome: COMPLETED (по видимому интерфейсу ревьюера). Отдельный вход студентом и фактическое получение уведомления не проверялись.

Роль: Елена Смирнова. Цель: первая сдача «Пагинация списка задач», курс «Практикум API · проверка работ». Другие работы не открывала и не изменяла. Только UI через выданный browser runner, без исходников, API, БД и проектных документов.

## Цели и доказательства

- Работа найдена в «Пул», «Основная очередь · первые проверки · попытка 1»; после «Начать проверку» появилась карточка «На проверке».
- Материал new-api.md открыт через «Открыть ↗». Русский текст повреждён кодировкой, однако видны GET /tasks, POST /tasks, JSON и 400; смысл короткого описания и трёх проверок частично восстанавливается из mojibake. Нормального читаемого материала получить через видимые элементы не удалось.
- Два требования найдены в карточке: «Основной сценарий API», «Ошибки и воспроизводимые проверки», каждое из 5. Порог 7/10. Полного описания задания или условий пагинации не нашла.
- Доступная помощь запущена кнопкой «Запустить проверку». Результат честно помечен «Локальный fixture», «Демонстрационная рекомендация. Реальная модель не вызывалась», по 2.5 балла и общий демо-отзыв.
- Собственное решение: 4/5 и 1/5, итого 5/10. Введены собственные обоснования и отзыв с конкретными негативными запросами, ожидаемыми ответами, проверкой отсутствия сохранения невалидной задачи, командами запуска и результатами. Оценка ограничена видимым материалом, реальный запуск студенческого API не проводился.
- Сохранён черновик; «Вернуть на доработку» открыло срок и поле «Что нужно исправить». Выставлено 08.09.2026 18:00, введены действия доработки. Диалог сообщил: «Студент получит сохранённый отзыв и оценку 5».
- Нажата «Подтвердить публикацию». После завершения карточка стала «Нужны правки», редактирование заменилось текстом отзыва, оценка 5/10, появилась «Создать исправление». В «Мои работы» у целевой строки «Нужны правки», «Проверить до: 8 сент.». Это видимое подтверждение завершённой публикации; отдельного сообщения «Опубликовано студенту» не было.

## Маршрут и ожидания

Мои работы → Пул → нужная первая попытка → Начать проверку → Открыть материал в новой вкладке → обратно → раскрыть второе требование → Запустить проверку → заменить оценки и отзыв → заполнить обоснования → Сохранить черновик → Вернуть на доработку → срок и правки → Подтвердить публикацию → проверить карточку → Мои работы.

Ожидала найти работу в личном списке, но её там не было; переход в пул быстро решил поиск. При раскрытии требования ожидала условия оценивания, увидела только обоснование. Кнопку помощи нашла под признаками генерации, ожидала проверку именно авторства, но она заполнила и ревью, и отзыв.

## Боли

1. Экран new-api.md: «API Ñ…», «Ð…». Ожидание: читаемый русский текст работы. Факт: mojibake, без видимого способа сменить кодировку/скачать. Влияние: нельзя уверенно проверить содержание. Минимальная идея: показывать текст UTF-8 в читаемом предпросмотре.
2. «Предварительное ревью от модели» и раскрытие требований. Ожидание: подробные условия задания рядом с баллами. Факт: только краткие названия, поле обоснования и затем демо-рекомендация. Влияние: трудно понять, за что именно ставить 4 или 5 и как связана пагинация с материалом. Идея: видимый текст требования и ссылка на полное задание.
3. «Запустить проверку» расположена под «Признаки генерации ИИ». Ожидание: проверить признаки генерации. Факт: заполнились оценки и ответ студенту. Влияние: действие имеет неожиданно широкий эффект. Идея: назвать «Получить предварительное ревью» и обозначить, какие поля заполнит.
4. «Локальный fixture» и зелёные ✓ при 1/5. Ожидание: галочка означает выполненное требование. Факт: зелёные галочки остаются у низкой оценки; показывается техническая демо-терминология. Влияние: неоднозначность статуса и доверия к оценке. Идея: явная подпись статуса рекомендации, нейтральная индикация и понятный текст демонстрационного режима.
5. Диалог «Что нужно исправить». Ожидание: использовать уже написанный отзыв. Факт: второе пустое поле, не объяснено, как соотносится с отзывом. Влияние: повторный ввод и риск расхождения. Идея: пояснить назначение или предложить взять текст из отзыва.
6. После публикации: «Ответ студенту / Уходит вместе с вердиктом», «Создать исправление». Ожидание: явное «Опубликовано» со сроком. Факт: успех выводится из статуса и исчезновения редактирования; структурированный срок в карточке не показан. Влияние: пришлось вернуться в список для дополнительного подтверждения. Идея: сообщение о публикации с оценкой и сроком, понятное название исправления решения.

## Инструментальная оговорка

Один мой ошибочный вызов fill использовал ID 17 после того, как изменение первой оценки добавило поле обоснования и сдвинуло ID второго балла. Вызов попал в summary, после чего мой обработчик получил TypeError: Cannot read properties of undefined (reading 'map'). Это ошибка автоматизации/участника, не UX-дефект продукта. По актуальному снимку использован ID 18, ввод продолжен без повторения ошибки. Остальные действия зависели от полученных UI controls. Прогон уложился в лимит 80 действий.

# Feature Specification: Интеграция с GitHub

**Feature Branch**: backend

**Created**: 2026-09-04

**Status**: Draft

**Input**: Приём разных GitHub-ссылок, доступ через GitHub App, фиксация версии и публикация человеческого отзыва

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Подключить GitHub-репозиторий (Priority: P1)

Студент прикладывает публичную или приватную GitHub-ссылку. Платформа проверяет доступ, объясняет требуемое подключение и показывает канонически распознанный артефакт до отправки.

**Why this priority**: Работа не может попасть в очередь, пока платформа не понимает репозиторий, версию и доступный путь.

**Independent Test**: Проверить публичный репозиторий, приватный репозиторий с установленным приложением и приватный репозиторий без доступа.

**Acceptance Scenarios**:

1. **Given** публичная поддерживаемая ссылка, **When** студент проверяет её, **Then** платформа показывает репозиторий, вид ссылки, версию и необязательный путь.
2. **Given** приватный репозиторий без доступа приложения, **When** студент проверяет ссылку, **Then** платформа объясняет, как предоставить доступ или запросить его у администратора репозитория.
3. **Given** доступ предоставлен, **When** preflight повторяется, **Then** ссылка становится доступной для сдачи.
4. **Given** репозиторий организации запрещает установку студентом, **When** подключение невозможно, **Then** платформа показывает необходимость одобрения владельца организации.
5. **Given** публичный репозиторий доступен для чтения без App, **When** проверяется канал обратной связи, **Then** платформа отдельно показывает отсутствие права публикации.

---

### User Story 2 — Зафиксировать проверяемую версию (Priority: P2)

После отправки платформа разрешает любую поддерживаемую ссылку в конкретный commit и получает ограниченный снимок работы. Ветка или Pull Request могут продолжать меняться, а итерация ревью остаётся связана с проверенной версией.

**Why this priority**: Отзыв должен однозначно относиться к содержимому, которое видел ревьюер.

**Independent Test**: Отправить ссылки на репозиторий, ветку, commit, Pull Request, tree и blob и проверить их каноническое представление.

**Acceptance Scenarios**:

1. **Given** ссылка на репозиторий, **When** она принимается, **Then** фиксируется текущая версия основной ветки.
2. **Given** ссылка на ветку, tree или blob, **When** она принимается, **Then** фиксируются полный commit и выбранный путь.
3. **Given** ссылка на Pull Request, **When** она принимается, **Then** фиксируются head repository, head commit, base repository и номер Pull Request.
4. **Given** ветка с символом slash и неоднозначным путём, **When** платформа разрешает ссылку, **Then** студент видит выбранные branch и subpath до отправки.
5. **Given** внешний источник изменился после начала ревью, **When** выполняется проверка перед публикацией, **Then** ревьюер завершает зафиксированную версию либо просит студента явно отправить новую.

---

### User Story 3 — Ограничить слишком большую работу (Priority: P3)

Платформа оценивает дерево и потоково получает архив в пределах установленных лимитов. Неподдерживаемые или слишком большие работы отклоняются до начала ревью.

**Why this priority**: Одна ссылка не должна исчерпать место или ресурсы self-hosted установки.

**Independent Test**: Проверить обычный репозиторий и fixtures, превышающие каждый установленный лимит.

**Acceptance Scenarios**:

1. **Given** репозиторий в пределах лимитов, **When** снимок получен и распакован, **Then** он становится версией артефакта.
2. **Given** усечённое или слишком большое дерево, **When** выполняется preflight, **Then** сдача отклоняется как слишком большая.
3. **Given** архив превышает лимит во время скачивания или распаковки, **When** предел достигнут, **Then** обработка прекращается с понятной ошибкой.
4. **Given** работа содержит LFS pointer или submodule, **When** содержимое нельзя воспроизвести, **Then** сдача отклоняется как неподдерживаемая.

---

### User Story 4 — Опубликовать отзыв в GitHub (Priority: P4)

После публикации локального ревью платформа отправляет человеческий отзыв в подходящий объект GitHub и сохраняет ссылку на результат.

**Why this priority**: Студент должен получить отзыв в привычном рабочем контексте.

**Independent Test**: Опубликовать результат для PR, обычной ветки и fork PR без доступа к base repository.

**Acceptance Scenarios**:

1. **Given** Pull Request и доступ к base repository, **When** публикуется отзыв, **Then** в PR появляется COMMENT review, связанный с проверенным head commit.
2. **Given** repo, branch, commit, tree или blob, **When** публикуется отзыв, **Then** появляется commit comment на проверенном SHA.
3. **Given** fork PR без права записи в base repository, **When** head repository доступен, **Then** отзыв публикуется комментарием к head commit и место заранее показано пользователю.
4. **Given** нет допустимой цели публикации, **When** локальное ревью опубликовано, **Then** GitHub-доставка становится видимым исключением, не отменяя локальный результат.
5. **Given** повторная итерация ревью, **When** публикуется новый отзыв, **Then** создаётся новый результат на новом SHA, а старый остаётся в истории.

### Edge Cases

- URL использует неподдерживаемый GitHub Enterprise hostname.
- Имя ветки содержит slash и совпадает с началом пути.
- Репозиторий пуст или удалён.
- Источник Pull Request удалён и head repository недоступен.
- Pull Request происходит из приватного fork.
- App установлена на head, но не на base repository.
- App имеет право чтения, но не публикации.
- Tree API возвращает усечённый результат.
- Архив меняет URL или истекает до скачивания.
- Фактический архив больше предварительной оценки.
- Репозиторий содержит LFS, submodule, бинарный файл или слишком много файлов.
- Ветка изменена или force-push выполнен во время ревью.
- Webhook доставлен повторно или не по порядку.
- GitHub принял публикацию, но платформа не получила однозначный ответ.
- Старая итерация ревью пытается опубликоваться после новой.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Платформа MUST принимать ссылки на GitHub repository, branch, commit, Pull Request, tree и blob.
- **FR-002**: Платформа MUST принимать только настроенные доверенные GitHub hostnames.
- **FR-003**: Каждая ссылка MUST разрешаться в канонический repository ID, полный commit SHA и необязательный subpath.
- **FR-004**: Студент MUST видеть распознанные repository, branch, SHA и subpath до отправки.
- **FR-005**: Неоднозначный branch/path MUST разрешаться через доступные сведения GitHub, а не только разбор строки.
- **FR-006**: Pull Request MUST фиксировать отдельные head и base repositories, head/base SHA и номер.
- **FR-007**: Версией работы Pull Request MUST быть head SHA, а не временный merge commit.
- **FR-008**: Отдельное подтверждение владения репозиторием MUST NOT требоваться.
- **FR-009**: Приватный доступ MUST предоставляться через ограничиваемую установку GitHub App.
- **FR-010**: Платформа MUST объяснять, когда установку должен одобрить администратор GitHub Organization.
- **FR-011**: Публичный репозиторий MUST быть доступен без обязательной установки App.
- **FR-012**: Preflight MUST проверять наличие репозитория, ref, пути и требуемых прав.
- **FR-013**: Ошибка private repository MUST отображаться как «не найден или нет доступа», не раскрывая его существование.
- **FR-014**: Платформа MUST применять отдельные лимиты числа файлов, размера одного файла, суммарных blob, скачанного архива и распакованных данных.
- **FR-015**: Получение и распаковка MUST прекращаться сразу после превышения соответствующего лимита.
- **FR-016**: Усечённое дерево MUST считаться превышением поддерживаемого объёма.
- **FR-017**: LFS и submodules MUST отклоняться в MVP, если их содержимое не входит в воспроизводимый снимок.
- **FR-018**: Успешный снимок MUST хранить каноническую ссылку, repository ID, SHA, subpath, время и контрольную сумму.
- **FR-019**: Push или изменение Pull Request MUST только отмечать новую доступную версию и MUST NOT автоматически создавать итерацию ревью.
- **FR-020**: Перед публикацией mutable source MUST повторно сравниваться с SHA итерации ревью.
- **FR-021**: При изменении source ревьюер MUST завершить проверку зафиксированной версии либо потребовать явную новую сдачу; текущая итерация ревью MUST NOT подменять свою Artifact Version.
- **FR-022**: Для доступного Pull Request платформа MUST публиковать COMMENT review в base repository.
- **FR-023**: Для остальных поддерживаемых ссылок платформа MUST публиковать commit comment на проверенном SHA.
- **FR-024**: Fork PR без записи в base MUST использовать commit comment в head repository, если он доступен.
- **FR-025**: Интерфейс MUST показывать цель GitHub-публикации до отправки.
- **FR-026**: Каждая доставка MUST сохранять внешний ID и URL опубликованного результата.
- **FR-027**: Повтор одной логической публикации MUST NOT создавать дубликат.
- **FR-028**: Новая итерация ревью MUST создавать новый отзыв на новой версии и сохранять старый.
- **FR-029**: Webhook MUST дедуплицироваться и не менять завершённую итерацию ревью без действия пользователя.
- **FR-030**: Ограничение частоты MUST приводить к отложенному повтору, а не потере доставки.
- **FR-031**: Отзыв доступа App MUST становиться видимой ошибкой и MUST NOT удалять сохранённые версии и отзывы.
- **FR-032**: Полномочия GitHub одной организации MUST NOT использоваться другой организацией.
- **FR-033**: Платформа MUST хранить достаточно диагностических данных для проверки URL, доступа, версии, размера, webhook и публикации через MCP.
- **FR-034**: Исполнение студенческого кода и AI-review MUST оставаться за границей этой функции.
- **FR-035**: Preflight MUST независимо определять возможность чтения артефакта и возможность публикации feedback.
- **FR-036**: Если GitHub-публикация обязательна, отсутствие write capability MUST стать requires action до завершения внешней доставки.

### Key Entities

- **GitHub Installation Binding**: разрешённая установка приложения и область репозиториев.
- **GitHub Artifact Reference**: исходный URL и его канонический вид.
- **GitHub Artifact Version**: repository ID, commit SHA, subpath и контрольная сумма снимка.
- **Pull Request Context**: head/base repositories, SHA и номер Pull Request.
- **Repository Preflight**: доступность, права, состав, размеры и обнаруженные ограничения.
- **GitHub Change Signal**: дедуплицированное уведомление о новой внешней версии.
- **GitHub Feedback Target**: PR review или commit comment для конкретного SHA.
- **GitHub Delivery**: публикация одного review revision и её внешний результат.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% поддерживаемых тестовых URL разрешаются в ожидаемые repository, SHA и subpath.
- **SC-002**: 100% неоднозначных branch/path fixtures либо разрешаются правильно, либо отклоняются до сдачи.
- **SC-003**: Публичная работа в пределах лимитов становится доступной для ревью не более чем за 2 минуты.
- **SC-004**: Приватный репозиторий без установки не раскрывает данные и показывает понятное действие подключения.
- **SC-005**: 100% fixtures, превышающих установленный лимит, прекращают обработку без превышения следующего защитного предела.
- **SC-006**: LFS и submodule fixtures не выдаются за полный воспроизводимый снимок.
- **SC-007**: Изменение ветки или PR до публикации обнаруживается в 100% приёмочных сценариев.
- **SC-008**: PR review или commit comment содержит проверенный SHA и доступную ссылку на локальный полный отзыв.
- **SC-009**: Повтор одной логической публикации создаёт не более одного GitHub-результата.
- **SC-010**: Fork PR без base write либо получает head commit comment, либо понятную ошибку до внешней публикации.
- **SC-011**: Для любой доставки методист видит target, внешний ID, время, попытки и полезную ошибку.
- **SC-012**: Отзыв GitHub-доступа не удаляет ни одной локально сохранённой версии или публикации.

## Assumptions

- Основной production-механизм доступа — GitHub App; сервисный пользователь с PAT не является основным контрактом.
- Пользователь, прикрепивший доступную ссылку, считается автором сдачи; авторство кода не проверяется.
- Доверенный hostname MVP — github.com; GitHub Enterprise настраивается отдельно.
- Inline review comments, REQUEST_CHANGES и issue-based feedback не входят в MVP.
- Числовые лимиты выбираются при планировании и одинаково применяются к preflight, скачиванию и распаковке.
- Студент или администратор репозитория способен предоставить приложению требуемый доступ.
- Webhook сообщает об изменении, а новая сдача создаётся только явным действием студента.
- Полный человеческий отзыв хранится локально; GitHub получает его представление и ссылку.

# Контракт внешнего AI-компонента: workspace v2

Бэкенд передаёт снимок работы и разрешённый контекст, принимает структурированные события и сохраняет результат. Внешний компонент реализует извлечение содержимого, промпты и проверку работы. Реализация транспорта проверяется локальными fixtures; совместимость с конкретным внешним компонентом пока не подтверждена.

## Схемы и примеры

Версия сообщений — `2.0.0`. Источник типов — `backend/src/review_platform/contracts/workspace.py`. JSON Schema экспортируются в каталог `contracts`:

- [SelfReviewRequest](contracts/self-review-request.schema.json) и [SelfReviewEvent](contracts/self-review-event.schema.json);
- [ReviewAssistRequest](contracts/review-assist-request.schema.json) и [ReviewAssistEvent](contracts/review-assist-event.schema.json).

[Примеры сообщений](contracts/examples) проходят валидацию соответствующими Pydantic-моделями. UUID, отпечатки, подписанные URL и содержательные выводы в них учебные. Адреса `example.invalid` не предоставляют файлы; для проверки скачивания используйте подписанные ссылки действующего локального запуска.

`self-review-succeeded.json`, `self-review-unsupported-format.json` и `self-review-all-not-checked.json` — альтернативные финалы одного примерного запуска. Не отправляйте их последовательно как историю одного запуска. То же относится к успешному и ошибочному финалам reviewer assist.

## HTTP transport

`REVIEW_PLATFORM_WORKSPACE_AI_URL` задаёт базовый адрес AI-сервиса. Бэкенд добавляет следующие пути:

| Назначение | Отправить запрос | Узнать исход |
|---|---|---|
| Самопроверка студента | `POST /v2/self-reviews/{run_id}` | `GET /v2/self-reviews/{run_id}?attempt=N` |
| Помощь ревьюеру | `POST /v2/review-assists/{run_id}` | `GET /v2/review-assists/{run_id}?attempt=N` |

POST содержит JSON request соответствующего типа. Оба метода передают `Idempotency-Key: {run_id}:{attempt}`. Если настроен `REVIEW_PLATFORM_WORKSPACE_AI_TOKEN`, оба метода передают `Authorization: Bearer <token>`. Проверка этого токена — обязанность принимающего AI-сервиса; cookie пользователя ему не передаётся.

| Ответ AI-сервиса | Поведение бэкенда |
|---|---|
| `200` + event JSON | Проверить схему, привязку и последовательность; принять событие |
| `202` или `204` | Оставить запуск в ожидании и продолжить lookup |
| `404` на GET | Исход пока неизвестен; продолжить lookup без повторного POST |
| Другой HTTP status, timeout, обрыв связи или неверный JSON | Считать исход неопределённым; сохранить запуск для восстановления |

Чтобы подтвердить технический отказ, верните `200` с событием `status: failed` и допустимым `error_code`. HTTP 500 сам по себе не подтверждает, что работа не выполнялась.

Transport не следует HTTP redirects. Вне local/test требуется HTTPS и явное включение live providers. Таймаут берётся из `REVIEW_PLATFORM_PROVIDER_TIMEOUT_SECONDS`; по умолчанию — 15 секунд. Проверка схемы применяется к ответам не более 2 МБ.

## Долговечность, повторения и порядок

AI-сервис должен сначала сохранить intent по `(run_id, attempt)`, затем выполнять работу. Повторный POST того же запуска не должен создавать вторую работу. `input_fingerprint` передаётся как непрозрачный идентификатор входа; верните его без изменений. Для той же пары run/attempt нельзя принять другой fingerprint.

Если ответ на POST потерян, новый backend worker делает GET. Он не повторяет POST по одному лишь отсутствию результата. Поэтому AI-сервису необходим долговечный lookup, который после восстановления возвращает сохранённый результат или подтверждённый отказ. Бесконечные 404 оставят пользовательский запуск в ожидании.

Каждое событие содержит `event_id`, `run_id`, `attempt`, `sequence` и `input_fingerprint`. `event_id` стабилен при повторной доставке одного события; его JSON не должен меняться. `sequence` монотонно увеличивается внутри попытки. Более старое событие не откатывает прогресс, а финальный результат не возвращается в running. Несовпадение run, attempt или fingerprint не принимается. Возвращайте одно последнее событие на GET, а не массив или поток SSE.

Reviewer assist позволяет явный повтор после подтверждённой ошибки в пределах серверного лимита попыток. Новая попытка имеет новый `attempt`; старые события не должны переопределять её результат. Неопределённый исход не разрешает создать повторную попытку автоматически.

## Снимок работы и форматы

`artifact_id` обозначает сохранённый снимок, `artifact_digest` — SHA-256 его байтов, `artifact_url` — временную подписанную ссылку для чтения. Скачайте байты, проверьте digest и работайте с этим снимком. Исходную изменяемую ссылку GitHub/Google Docs AI-сервис не получает как замену артефакта.

Подготовленные материалы могут иметь MIME type Markdown (`text/markdown`), PDF (`application/pdf`), DOCX (`application/vnd.openxmlformats-officedocument.wordprocessingml.document`) и архив подготовленного GitHub-снимка (`application/zip`). Ориентируйтесь на фактический `media_type` запроса; наличие upload в интерфейсе не доказывает поддержку формата вашей моделью. Если компонент не умеет обработать полученный формат, отправьте финальное событие `failed` с `unsupported_format`. Не возвращайте выдуманную успешную проверку.

Ссылка выдаётся на ограниченный срок: самопроверка использует 15 минут, reviewer assist — `REVIEW_PLATFORM_AI_SIGNED_URL_TTL_SECONDS` (по умолчанию 15 минут). Скачивайте снимок при приёме POST. GET восстановления не передаёт обновлённую ссылку: сервис должен сохранить необходимые байты или вернуть подтверждённую ошибку. `reference_url` в reviewer assist также временная и содержит приватный эталон.

## Разделение контекста и результатов

| | Самопроверка студента | Помощь ревьюеру |
|---|---|---|
| `purpose` | `student_self_review` | `reviewer_assist` |
| Контекст | Работа, публичное условие и публичные критерии с максимумами | Работа, условие, полный набор критериев с описаниями, указания ревьюеру и возможный приватный эталон |
| Результат | `findings`: статус, обратная связь, свидетельство | `suggestions`: возможные баллы, основание, свидетельства, уверенность, заметка ревьюеру и текст для студента |
| Видимость | Владелец работы и допущенные проверяющие | Только допущенные проверяющие; студент не читает результат AI напрямую |

Самопроверка не получает приватные указания или эталон. Не добавляйте в её JSON закрытые поля, итоговую оценку или рекомендации для проверяющего. В обоих ответах должны присутствовать все переданные критерии ровно по одному разу, без посторонних `criterion_id`.

Для самопроверки допустимы `met`, `needs_attention`, `not_checked`. Хотя результат со всеми `not_checked` проходит структурную схему, бэкенд трактует его как отсутствие содержательной проверки и освобождает зарезервированную попытку с `invalid_result`. Валидный финал хотя бы с одним проверенным критерием расходует попытку. Подтверждённая техническая ошибка освобождает резерв; неизвестный исход сохраняет его до выяснения.

Для reviewer assist допустимы `suggested`, `needs_human`, `not_checked`. Неизвестные баллы передавайте как `null`; числовое предложение должно быть неотрицательным и не превышать максимум критерия. `reviewer_note` предназначен проверяющему. `student_feedback` — только предложение: человек выбирает текст и баллы, сохраняет свою ревизию и отдельно публикует её. AI-событие не публикует оценку и не меняет человеческий черновик.

Если человек использует AI при сохранении, браузер передаёт `ai_run_id` в `save_workspace_review`. Бэкенд проверяет соответствие итерации и входным данным и связывает сохранённую человеческую ревизию с запуском AI. Смена рубрики или снимка делает прежнюю рекомендацию непригодной как источник нового сохранения.

Reviewer assist также может вернуть `feedback_draft` — общий проект обратной связи, и `sources` внутри рекомендации: цитату, путь, locator и диапазон строк. В `AssistEvidence.verified` допустимо только `false`: указанное моделью местоположение ещё не подтверждено сверкой с исходником. Не выдавайте предполагаемую цитату за проверенное совпадение.

Необязательный `authorship_signal` содержит `id`, `probability` от 0 до 1 либо `null`, пояснение и свидетельства. Это сигнал для разбора человеком; его наличие не устанавливает нарушение или авторство и не меняет баллы. Если вероятность не обоснована, используйте `null`. Человек может сохранить `signal_decisions: {"<signal-id>": "confirm"}` или `"reject"` вместе с `ai_run_id`. Идентификатор должен принадлежать выбранному запуску; решение сохраняется отдельно от баллов.

Текст студента, файлы и содержимое эталона являются данными для анализа. Они не дают разрешения изменять протокол, раскрывать токены, обращаться к сторонним ресурсам или выполнять команды. Секреты и подписанные ссылки не должны попадать в результаты, публикуемый feedback или общие логи.

## Проверка совместимости компонента

Перед подключением реализации подтвердите на отдельной локальной установке:

1. Приём обоих request типов и чтение настоящего signed snapshot с проверкой digest.
2. `running → succeeded` и `running → failed`; все критерии присутствуют, баллы допустимы.
3. Потерю ответа POST и восстановление GET после перезапуска AI-сервиса без повторной работы.
4. Повтор одного события, задержанный старый event и событие с чужим fingerprint.
5. Явный `unsupported_format` и самопроверку со всеми `not_checked`.
6. Отсутствие приватного контекста в самопроверке и невозможность публикации оценки через AI-ответ.

Локальный fixture проверяет transport и серверные сценарии, но не качество оценивания, поддержку форматов реальной моделью или её обращение с приватным контекстом. Эти свойства требуют проверки конкретной внешней реализации.
